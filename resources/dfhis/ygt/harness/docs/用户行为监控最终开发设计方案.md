# 用户行为监控最终开发设计方案

## 1. 目标边界

用户行为监控属于医共体主应用的平台观测能力，不承载患者业务 CRUD。主应用负责统一采集、脱敏、接收、存储和查询追溯，具体业务页面只负责在关键动作发生时调用监控 SDK。

最终目标：

1. 记录谁在什么时间、什么租户、什么机构、什么页面、做了什么动作。
2. 同一页面访问通过 `pageViewId` 串联，同一请求链路通过 `traceId` 串联。
3. 患者、表单、导出、打印等敏感资源只记录 `resourceIdHash`，不记录姓名、身份证、手机号、地址、诊断等明文。
4. 前端先脱敏，后端二次脱敏，数据库只落清洗后的 `data_json`。
5. 监控失败不阻塞主业务，但后端会在响应中返回 `storageReady=false` 方便部署检查。

## 2. 分阶段落地目标

### P2 后端接收与落库

范围：

1. 新增 `POST /oauth2/monitor/events` 批量接收接口，同时兼容 `POST /monitor/events` 和 `POST /api/monitor/events`。
2. 新增后端 DTO、二次脱敏、批量校验、批量落库。
3. 新增 `backend/sql/02-ygt-monitor-event-ddl.sql`。
4. 新增 `GET /oauth2/monitor/events` 查询接口，同时兼容 `GET /monitor/events` 和 `GET /api/monitor/events`。

完成标准：

1. 单批默认最多 100 条。
2. 单条坏数据只跳过该条，整批不失败。
3. 表未创建时返回 `storageReady=false`，不影响前端主流程。
4. 后端单测覆盖脱敏、批量接收、表未就绪、双路径控制层契约。

### P3 前后端联调与追溯

范围：

1. 前端默认上报和查询地址使用 `/oauth2/monitor/events`，确保本地 Vite 与生产网关都走同一条可达链路。
2. 保留 `runtimeConfig.monitor.endpoint` 覆盖能力。
3. 通过 `traceId`、`pageViewId`、`actionCode`、`resourceType`、`userId`、时间区间查询。

完成标准：

1. 前端监控测试覆盖默认 endpoint、鉴权头、批量 body。
2. 主前端 typecheck/build 通过。
3. 后端 test/package 通过。

### P4 审计运营化

范围：

1. 基于 `GET /oauth2/monitor/events` 做审计查询页面，并在同一页面提供运维状态条。
2. 高风险事件包括导出、打印、配置保存、患者详情查看、表单提交等。
3. 可按 `riskLevel=high`、`resourceType=patient`、`actionCode=EXPORT_CLICK` 做专项审计。
4. 支持按选中事件的 `traceId` 或 `pageViewId` 快速追踪同链路事件。
5. 审计查询页 `/system/audit/monitor-events` 及其 `/redirect/system/audit/monitor-events` 跳转态不参与监控采集，查询接口默认通过 `excludeRoutePath` 排除历史自噪声。

完成标准：

1. 审计查询页面只展示脱敏字段。
2. 管理端支持按用户、页面、资源哈希和时间区间定位行为链。
3. 页面展示存储就绪状态、接口地址、结果总数、本页高风险数量、最近接收时间和最后刷新时间。
4. 审计查询页自身的打开、刷新、查询、翻页、按钮点击不污染审计统计。
5. 数据库保留策略、归档策略由运维/合规配置决定。

### P5 监控范围策略配置

范围：

1. 新增 `ygt_monitor_policy` 策略表和 `backend/sql/03-ygt-monitor-policy-ddl.sql`，用于配置页面路径、匹配方式、采集模式、事件类型、动作编码和优先级。
2. 新增 `GET /oauth2/monitor/policies/effective` 供前端启动加载生效策略，同时兼容 `/monitor/policies` 和 `/api/monitor/policies`。
3. 新增 `GET /oauth2/monitor/policies`、`POST /save`、`POST /toggle`、`POST /remove` 支持监控策略配置页维护。
4. 前端监控 SDK 在入队前执行策略过滤，后端事件入库前再次执行策略过滤，避免旧前端包或缓存绕过排除规则。
5. 新增 `/system/audit/monitor-policies` 策略配置页，并通过 `backend/sql/04-ygt-monitor-audit-menu.sql` 初始化功能、菜单和系统管理员授权。

完成标准：

1. 内置强制排除 `/system/audit/monitor-events`、`/system/audit/monitor-policies` 及其 `/redirect/...` 跳转态；即使策略表未建也生效。
2. 普通策略支持 `exact`、`prefix`、`contains` 三种页面匹配，支持 `full`、`off`、`audit_only`、`track_only`、`error_only` 五种采集模式。
3. 策略页内置强制策略只读，普通策略可新增、保存、启停、删除。
4. 患者 360 默认保留重点采集策略，运维可在策略页按实际合规要求调整或停用。
5. 策略接口异常时前端继续使用缓存与内置兜底策略，后端策略检查异常时默认采集，避免关键审计事件因策略表短暂异常丢失。

## 3. 患者 360 打开页面如何记录

用户打开患者 360 时，前端生成一条页面访问事件：

```json
{
  "events": [
    {
      "eventId": "evt_patient360",
      "schemaVersion": "1.0",
      "eventType": "track",
      "eventName": "page_view",
      "occurredAt": "2026-06-29T10:00:00.000Z",
      "appName": "df-web-ygt-main",
      "microApp": "biz-zhusuoyin",
      "routePath": "/biz-zhusuoyin/patient360",
      "pageViewId": "pv_xxx",
      "sessionId": "sess_xxx",
      "traceId": "trace_xxx",
      "actionCode": "MENU_OPEN",
      "resourceType": "patient",
      "resourceIdHash": "h_patient_xxx",
      "riskLevel": "low",
      "result": "success",
      "data": {
        "entry": "/biz-zhusuoyin/patient360",
        "source": "menu"
      }
    }
  ]
}
```

后端最终落库到 `ygt_monitor_event` 的核心字段：

| 字段 | 示例 | 说明 |
| --- | --- | --- |
| `event_id` | `evt_patient360` | 前端事件 ID，用于重试去重 |
| `event_type` | `track` | 页面行为事件 |
| `event_name` | `page_view` | 页面访问 |
| `action_code` | `MENU_OPEN` | 标准动作编码 |
| `route_path` | `/biz-zhusuoyin/patient360` | 只保留 pathname |
| `page_view_id` | `pv_xxx` | 串联同一页面内后续点击、导出、打印 |
| `session_id` | `sess_xxx` | 前端会话 |
| `trace_id` | `trace_xxx` | 请求链路追踪 |
| `user_id` | 当前用户 | 后端上下文优先补齐 |
| `tenantid` | 当前租户，缺省 `0` | 后端上下文优先补齐 |
| `org_id` / `dept_id` | 当前机构/科室 | 后端上下文优先补齐 |
| `resource_type` | `patient` | 资源类型 |
| `resource_id_hash` | `h_patient_xxx` | 患者 ID 哈希，不存原始 ID |
| `risk_level` | `low` | 打开页面为低风险 |
| `data_json` | 脱敏 JSON | 不含患者姓名、身份证、手机号等明文 |

如果同一页面里继续点击打印，前端会追加一条 `actionCode=PRINT_CLICK`、`riskLevel=high` 的事件，并复用同一个 `pageViewId`，审计时即可还原“打开患者 360 -> 打印”的行为链。

## 4. 安全规则

后端会删除以下敏感 key 或其变体：

1. 患者姓名、真实姓名。
2. 身份证、手机号、电话、地址。
3. 诊断、表单原文、EMPI 原文。
4. token、authorization、cookie、password、secret、clientSecret。

后端会掩码以下文本内容：

1. 身份证号替换为 `[REDACTED_ID_CARD]`。
2. 手机号替换为 `[REDACTED_MOBILE]`。
3. Bearer token 替换为 `Bearer [REDACTED]`。
4. URL 只保留 pathname。

## 5. 页面排除如何生效

以排除 `/system/audit/monitor-events` 为例：

1. 前端启动后调用 `/oauth2/monitor/policies/effective`，拿到内置策略 `collectMode=off`、`routePattern=/system/audit/monitor-events`。
2. 用户打开审计查询页时，`track('page_view')` 会先构造事件，再在入队前匹配策略；命中 `off` 后不进入队列。
3. 如果前端没加载到策略，SDK 仍有同一组内置排除规则。
4. 如果旧前端包仍上报了该事件，后端 `MonitorEventService` 在写入 `ygt_monitor_event` 前再次调用策略服务，命中后把该条放入 `skipped`，不落库。
5. 查询页自身还会在查询接口传 `excludeRoutePath`，用于排除历史已经产生的自噪声。

策略匹配优先级：

1. 只匹配启用策略。
2. 先按 `priority` 升序，越小越优先。
3. 同优先级下页面表达式越长越优先。
4. 第一条命中的策略决定采集模式。

## 6. 上线检查

1. 先在目标库执行 `backend/sql/02-ygt-monitor-event-ddl.sql`。
2. 执行 `backend/sql/03-ygt-monitor-policy-ddl.sql` 初始化策略表。
3. 在基础服务库执行 `backend/sql/04-ygt-monitor-audit-menu.sql` 初始化功能菜单和系统管理员授权。
4. 启动主应用后调用 `POST /oauth2/monitor/events`，确认响应 `storageReady=true` 且 `persistedCount > 0`。
5. 调用 `GET /oauth2/monitor/events?traceId=...` 或 `GET /oauth2/monitor/events?pageViewId=...`，确认能查回事件。
6. 打开 `/system/audit/monitor-events` 和 `/system/audit/monitor-policies`，确认后续查询结果不再新增这两个页面的 `page_view` 或 `button_click`。
7. 打开 `/system/audit/monitor-policies`，新增一条 `collectMode=off` 的测试页面策略，确认前端入队和后端落库均被排除。
8. 抽查 `data_json`，不得出现患者姓名、身份证、手机号、token、cookie、password 等明文。
9. 前端生产网关需同源转发 `/oauth2/monitor` 到主应用后端。
