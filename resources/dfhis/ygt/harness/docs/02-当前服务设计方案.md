# 02 - 当前服务设计方案

## 系统架构

当前仓库一期采用“前端 Shell 主应用 + 后端主应用认证聚合服务 + 后续业务领域子服务”的结构。

0. `apis/` 作为跨服务调用契约模块，统一沉淀基于 `@HttpExchange` 的声明式接口与共享 DTO，并内置消费端代理自动装配；provider 不要求 implements 契约接口。
1. 前端主应用为 `frontend/df-web-ygt-main`，承担微前端容器、认证态承接、路由装配、菜单承载与工作台聚合。
2. 后端主应用为 `backend`（服务标识为 `df-ygt-main`），承担 OAuth2 认证、客户端治理、用户主体承接、权限菜单聚合与门户聚合能力。
3. 用户密码校验不在主应用本地完成，而是通过服务发现调用基础业务服务 `df-ygt-biz-base` 暴露的登录校验接口 `POST /api/sys/yonghu/verify-password`。
4. 认证服务基于 Spring Authorization Server 落地，统一对外提供标准 OAuth2 端点；下游业务服务继续使用共享 `df.security.jwt.secret` 解析 HS256 token。
5. 本期 OAuth2 交付范围收敛为两类授权模式：`client_credentials` 与 `password`。`authorization_code`、OIDC userinfo、前端 PKCE/Consent 页面编排属于后续规划，不作为本期已实现能力描述。

整体调用链如下：

1. 客户端通过 `/oauth2/token` 向主应用申请 token。
2. `client_credentials` 直接由 Spring Authorization Server 原生流程签发 token。
3. `password` 由主应用的自定义 Password Grant Converter/Provider 接管，转调 `df-ygt-biz-base` 的 `verify-password` 接口完成用户名密码验证。
4. 验证通过后，主应用签发 access token / refresh token，并将授权记录持久化到 JDBC 表。
5. 下游服务通过共享密钥解析 token，并从 claims 中获取 `tenantId`、`userId`、`userName`、`client_id` 等上下文信息。

## 服务列表

| 服务名 | 职责 | 技术栈 | 端口 |
|--------|------|--------|------|
| `df-ygt-main` | OAuth2 认证服务、客户端管理、JWT 签发、门户与权限聚合 | Java 25、Spring Boot 4.0.5、Spring Authorization Server、df-core-starter、df-cloud-starter、df-jpa-starter、df-tenant-starter、df-redis-starter | 8101 |
| `df-ygt-biz-base` | 基础业务服务，提供用户、菜单、机构、权限等基础数据能力；本方案中承接用户名密码校验 | Java 25、Spring Boot 4.0.5、df-* starters | 由 Nacos 配置决定 |
| `df-web-ygt-main` | 前端 Shell 主应用，承接登录态、菜单、微前端容器与门户展现 | Vue 3、TypeScript、Vite、qiankun、Pinia | 前端开发端口按 Vite 配置 |

说明：

1. `df-ygt-main` 的代码目录位于 `backend/`，服务标识与 Nacos DataId 按 `df-ygt-main` 维护。
2. `apis/` 当前用于沉淀跨服务远程调用契约，接口定义基于 `@HttpExchange`，通过自动配置扫描 `@YgtRemoteApi` 接口后批量注册代理；consumer 引入依赖即可直接注入使用，无需逐个手工声明 `@Bean`。provider 若复用同一模块，职责是复用 DTO 与契约定义，不以 controller implements 契约接口作为默认实现方式。
3. 当前仓库为了快速落地，契约定义与消费端自动装配仍放在同一个 `apis/` 模块中；这不影响现阶段使用。若后续 provider 侧也需要长期、广泛依赖该模块，并希望严格隔离“共享契约”和“客户端装配”，再拆分为 `contract` 与 `client-starter` 两个模块。
4. `df-ygt-biz-base` 通过 Nacos 服务发现被认证服务调用，当前已确认其 `spring.application.name` 为 `df-ygt-biz-base`。
5. 认证相关敏感配置（数据库、JWT 密钥、客户端初始化参数）统一放在 Nacos，不回填本地 `application.yml`。

## API 设计

### 1. 标准 OAuth2 端点

主应用基于 Spring Authorization Server 提供标准端点，统一以 `/oauth2/*` 为主：

1. `POST /oauth2/token`
	用于申请 access token。
2. `POST /oauth2/revoke`
	用于撤销 token。
3. `POST /oauth2/introspect`
	用于服务间 introspection（按需开放）。
4. `GET /.well-known/oauth-authorization-server`
	用于暴露授权服务器元数据。
5. `GET /oauth2/jwks`
	若后续切换 JWK 暴露策略可启用；本期 HS256 下主要使用共享密钥解析。

本期不额外交付 demo 中的 `/oauth/token` 包装接口，避免与标准 OAuth2 端点重复。

### 2. 本期支持的授权模式

#### 2.1 client_credentials

适用场景：

1. 后端服务对后端服务调用。
2. 定时任务、批处理、内部系统集成。

请求示例：

1. `grant_type=client_credentials`
2. 通过 `Authorization: Basic base64(client_id:client_secret)` 传递客户端凭证。
3. 可附带 `scope`。

处理原则：

1. 复用 Spring Authorization Server 原生 `client_credentials` provider。
2. 客户端信息从 JDBC 注册客户端仓储中读取。
3. scope 必须是客户端已授权 scope 的子集。
4. token claims 中写入 `client_id`、`grant_type`、`scope`，不写入用户主体字段。

#### 2.2 password

适用场景：

1. 当前医共体内部受控登录场景。
2. 历史系统仍以“用户名 + 密码”直接换 token 的兼容接入。

说明：

1. `password` 模式属于 OAuth2 新规范中不再推荐的兼容扩展，本项目仅在内部受控场景保留，不作为长期演进方向。
2. 本项目通过自定义 `OAuth2PasswordAuthenticationConverter` 与 `OAuth2PasswordAuthenticationProvider` 扩展 Spring Authorization Server 的 token 端点。

请求参数约定：

1. `grant_type=password`
2. `username`
3. `password`
4. `tenantId`：建议作为扩展参数显式传入；若缺失，再兜底读取请求头 `X-Tenant-Id`
5. `scope`：可选

处理流程：

1. token 端点收到 `grant_type=password` 请求后，由自定义 converter 解析表单参数。
2. provider 从参数中提取 `tenantId`、`username`、`password`、客户端信息。
3. provider 通过 `RestClient` 调用 `df-ygt-biz-base` 的 `POST /api/yonghu/verify-password`。
4. 若远程响应 `yzJg=1`，则使用返回的用户主体信息组装认证主体并签发 token。
5. 若远程响应 `yzJg=0`，则按 `shiBaiYydm` 映射为 OAuth2 `invalid_grant`，并保留诊断日志。

远程验密接口契约：

请求 DTO：`DTO_YongHu_DengLuYz`

1. `tenantId`：租户 ID，必填
2. `yongHuMc`：登录名称，必填
3. `miMa`：明文密码，必填
4. `keHuDuanIp`：客户端 IP，可选

响应 DTO：`DTO_YongHu_DengLuYzJg`

1. `yzJg`：0 失败，1 成功
2. `shiBaiYydm`：失败原因代码，例如 `USER_NOT_FOUND`、`PASSWORD_WRONG`、`ACCOUNT_DISABLED`、`ACCOUNT_LOCKED`、`ACCOUNT_EXPIRED`、`TENANT_REQUIRED`
3. `shiBaiYy`：失败原因描述
4. `shengYuCs`：剩余尝试次数
5. `suoDingDqsj`：锁定到期时间
6. `yongHuId`、`yongHuMc`、`zhenShiXm`、`jiGouId`、`keShiId`、`zhiGongId`、`yongHuLx`、`tenantId`：成功后的用户身份信息

### 3. Token 设计

本期 token 签发策略如下：

1. 签名算法：`HS256`
2. 密钥来源：共享 `df.security.jwt.secret`
3. access token：由主应用签发，用于业务服务鉴权
4. refresh token：对 `password` 模式与允许刷新令牌的客户端开放

claims 设计：

#### client_credentials claims

1. `client_id`
2. `grant_type=client_credentials`
3. `scope`

#### password claims

1. `client_id`
2. `grant_type=password`
3. `scope`
4. `tenantId`
5. `userId`
6. `userName`
7. `zhenShiXm`
8. 可按需增加 `jiGouId`、`keShiId`、`yongHuLx`

字段命名原则：

1. 对齐当前项目请求上下文与租户约定，避免沿用 demo 中旧版字段名。
2. 以业务服务易消费为目标，避免 claims 里重复塞入整份用户对象。

### 4. 客户端注册与持久化

本期客户端与授权数据全部走 JDBC 持久化，不采用内存模式。

使用的核心表：

1. `oauth2_registered_client`
2. `oauth2_authorization`
3. `oauth2_authorization_consent`

设计原则：

1. 优先采用 Spring Authorization Server 官方 schema，避免照搬 demo 中的自定义客户端模型。
2. `client_secret` 必须加密存储。
3. `authorization_grant_types` 需要显式包含 `client_credentials` 或 `password`。
4. `client_settings`、`token_settings` 通过 JSON 持久化，支持控制 refresh token、生存期、reuse 策略等。

后续若需要后台管理客户端，可在 auth 域中增加内部管理接口，但不影响标准 token 端点。

### 5. 安全配置边界

1. 授权服务器端点链路与普通资源访问链路分两条 `SecurityFilterChain`。
2. `/oauth2/token`、`/oauth2/revoke`、`/oauth2/introspect` 等端点由 SAS 配置接管。
3. 默认资源服务链路继续支持 Bearer token 解析。
4. 主应用自身的管理接口与后续门户聚合接口，可作为资源服务受保护资源处理。
5. 本期不实现自定义登录页面、授权确认页面、前端 SSO 跳转编排。

## 关键流程

### 1. client_credentials 获取 token

1. 调用方使用 `client_id` 与 `client_secret` 发起 `POST /oauth2/token`。
2. SAS 校验客户端身份。
3. 校验 grant type 与 scope 是否匹配客户端注册信息。
4. 生成 access token。
5. 将授权结果写入 `oauth2_authorization`。
6. 返回 Bearer token。

### 2. password 获取 token

1. 调用方发起 `POST /oauth2/token`，携带 `grant_type=password`、`username`、`password`、`tenantId`。
2. 自定义 converter 解析请求并组装 Password Grant AuthenticationToken。
3. 自定义 provider 调用 `df-ygt-biz-base` 的 `POST /api/yonghu/verify-password` 进行远程用户名密码校验。
4. 若校验成功，组装当前用户主体。
5. 生成 access token 与 refresh token。
6. 将授权结果写入 `oauth2_authorization`。
7. 返回 Bearer token 与 refresh token。

### 3. password 错误链路

1. 用户名不存在、密码错误、账号锁定、账号作废、账号过期等失败场景，由 `df-ygt-biz-base` 返回 `yzJg=0`。
2. 主应用不把这类业务失败当作 500 处理，而是映射为 OAuth2 标准错误响应。
3. 返回值对外遵循 OAuth2 错误结构；内部日志保留 `shiBaiYydm` 便于排查。

### 4. 下游服务消费 token

1. 下游服务从请求头读取 Bearer token。
2. 使用共享 `df.security.jwt.secret` 按 HS256 解析 JWT。
3. 从 claims 中提取 `tenantId`、`userId`、`userName`、`client_id`、`grant_type`。
4. 结合 `X-Tenant-Id` 与业务服务自身权限模型完成鉴权和上下文建立。

## 验收口径

本方案落地后，至少需要完成以下验证：

1. `client_credentials` 成功获取 token。
2. `password` 成功获取 token。
3. `password` 错误密码场景返回标准 OAuth2 错误，而不是 500。
4. 使用 token 访问受保护接口时，可成功解析 claims。
5. `oauth2_registered_client`、`oauth2_authorization` 表中可见正确落库记录。
6. 文档、配置、代码三者口径保持一致，不把后续规划写成已实现。
