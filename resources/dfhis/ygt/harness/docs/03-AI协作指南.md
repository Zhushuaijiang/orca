# 03 - AI 协作指南

本项目是医共体平台主应用，包含后端认证与门户聚合服务，以及前端 qiankun Shell。AI 开发时先判断任务属于后端主应用、前端 Shell、子应用注册，还是跨服务联调。

本指南参考 `andrej-karpathy-skills` 的四个协作原则：先澄清假设、保持简单、精准修改、用可验证目标闭环。

## 1. 开工前先回答

1. 本次任务是否属于主应用职责，还是应该落到某个 `df-ygt-biz-*` 业务服务？
2. 是否涉及认证、用户、权限、菜单、租户、门户聚合或前端 Shell？
3. 前端任务是否涉及 qiankun 注册、布局、路由、状态、消息或共享上下文？
4. 后端任务是否已阅读 [后端开发指南](后端开发指南/README.md) 01 到 04？
5. 成功标准是什么，最小验证命令是什么？

如果需求是患者、机构、字典、主索引等具体业务能力，默认不在主应用落地，只在主应用做入口、聚合或认证授权配合。

## 2. 项目边界

本项目负责：

1. OAuth2 认证入口、用户主体映射、client 管理、token 颁发与校验。
2. 菜单、权限、门户工作台、跨服务待办与消息聚合。
3. 前端 Shell 的登录、布局、路由、qiankun 微应用装载、共享上下文和消息中心。
4. 通过标准协议调用业务子服务，不下沉具体业务领域实现。

具体能力是否已经落地以当前 README、文档和代码为准，规划中能力不要写成已实现。

本项目不负责：

1. 患者 360、基础数据、字典、主索引等具体业务接口实现。
2. 业务子应用内部页面编排。
3. 在主应用内复制业务服务的 Entity、Repository 或 Service。
4. 在 `application.yml` 写数据库、Redis 等运行配置。

## 4. 后端 AI 规则

1. Controller 返回业务对象，由脚手架统一包装为 `R<T>`，不要新增第二套响应壳。
2. 业务异常使用 `BusinessException` 和 `CommonErrorCode`。
3. 实体继承 `BaseEntity`，Repository 继承 `BaseRepository`。
4. DTO 继承 `DTOBase`，批量接口按 `DTOState` 分流。
5. 分布式 ID 用 `SequenceUtil`，DTO 与 Entity 转换优先用 `ConverterUtil`。
6. JWT 相关逻辑复用 `JwtTokenService`，不要自造 token 服务。
7. 查询用 GET，新增、修改、删除、批量统一 POST。
8. Nacos 分层配置：`application.yml` 只保留引导，服务配置进 `df-ygt-main.yaml`。

## 5. 前端 AI 规则

1. 先判断是 Shell 通用能力，还是某个业务子应用能力。
2. 新增子应用时先确定 `name`、`defaultEntry`、`activeRule`、`title`、`mode`、provider 路径。
3. 普通页面型子应用使用 `route`，共享能力 provider 使用 `silent`。
4. 不要手动维护从注册表可推导出的列表。
5. 不要把业务页面放进 Shell；Shell 只做容器、布局、会话、聚合入口。
6. 主应用运行时配置统一在 `config/apps/apps.prod.js` 和 `config/apps/apps.dev.js` 中维护。

## 6. 禁止事项

1. 不要在主应用实现患者、字典、主索引等业务领域 CRUD。
2. 不要在后端模块创建新的统一响应、统一异常、错误码体系、ID 生成器或 DTO 基类。
3. 不要把敏感连接信息写进仓库。
4. 不要为了修一个子应用注册问题重写 qiankun 初始化流程。
5. 不要把规划中能力写成已实现能力。

## 7. 最小验证

后端：

```powershell
$env:JAVA_HOME='D:\Program Files\Java\jdk-25.0.2.10-hotspot'
mvn -f backend/pom.xml test
mvn -f backend/pom.xml clean package -DskipTests
```

前端 Shell：

```bash
cd frontend/df-web-ygt-main
pnpm typecheck
pnpm build
```

联调任务还要至少验证：成功链路、参数校验失败链路、业务异常链路。

## 8. 成功标准

1. 改动严格落在主应用职责边界内。
2. 后端复用 df-java-base 能力，前端复用 Shell 既有模式。
3. 子应用注册同时覆盖生产和开发配置。
4. 文档、配置、代码口径一致。
5. 验证命令或手工联调结论明确记录。
