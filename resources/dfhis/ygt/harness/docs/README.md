## 4. 文档职责边界

1. 根目录 `01` 到 `04` 是阅读主线，只维护项目概览、当前设计、AI 协作和 harness 闭环。
2. 前端规则只在 `前端开发指南/` 维护；涉及布局、查询栏、按钮、DevExtreme、生产 Nginx 时以该目录为准。
3. 后端规则只在 `后端开发指南/` 维护；涉及统一响应、异常、DTO、Entity、Repository、Nacos、日志、接口风格时以该目录为准。
4. AI 协作和闭环执行以 `03-AI协作指南.md` 和 `04-YGT工作流Harness.md` 为准。
5. 凭据、token、密码不进入仓库文档或可提交脚本；本地私密环境文件只在 `.gitignore` 覆盖范围内使用。

## 5. 当前 harness 主线

一句话入口：

```powershell
node scripts/harness/ygt-workflow.mjs /ygt "这里写需求或缺陷" --project auto --json
```

返回的 `standards` 是动手前必读清单；返回的 `commands` 是本次任务推荐闭环。一般顺序是：

```text
intake -> impact -> doctor -> 修改 -> verify --profile standard --changed-only -> review -> report
```

修改 harness、插件、安装脚本或工作流文档时，还要跑：

```text
selftest -> report --with-selftest
```

需要发布时再进入：

```text
commit -> push -> doctor -> jenkins -> rollout -> smoke -> report
```

完整命令说明见 [04-YGT工作流Harness.md](04-YGT工作流Harness.md)。

## 6. 维护规则

1. 新增规范前先判断是否已有权威位置，避免在 FAQ、概述和指南里复制同一段规则。
2. 删除旧口径时优先保留链接和迁移说明，让读者知道应该去哪里看正文。
3. harness 命令或参数变化时，同步更新 `04-YGT工作流Harness.md`。
4. 前后端代码模式变化时，同步更新对应开发指南，不把代码事实只留在单次会话里。
5. 示例工程和模板可以用于复制，但不得反向覆盖主规范；若示例与主规范冲突，以主规范为准。
