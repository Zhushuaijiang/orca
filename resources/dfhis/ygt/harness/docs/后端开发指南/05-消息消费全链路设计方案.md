# 05-消息消费全链路设计方案

## 1. 设计目标

`df-message-starter` 的消息能力从轻量 RabbitMQ 发布监听升级为持久化消息链路。业务发送消息必须先进入数据库主账本，事务提交后再投递到传输通道；消费侧必须先记录消费账本，再执行业务监听方法；后台定时任务负责发送补投、消费超时对账、告警与补发。

本方案的事实来源是业务数据库，不以 Redis、RabbitMQ 或 Elasticsearch 作为主账本。Redis 与 RabbitMQ 只承担传输通道职责。

## 2. 已确认决策

1. 持久化主存储采用业务数据库/JPA。
2. Redis 与 RabbitMQ 采用全局二选一模式，通过 `df.message.mode=redis|rabbitmq` 切换。
3. Redis 统一要求 5.0+，第一版唯一 Redis 消费通道采用 Redis Stream + Consumer Group，不使用 Pub/Sub 承载消费链路。
4. 队列维护、配置管理、发布、下线属于业务管理能力，放在 `df-ygt-biz-base` 后端与对应前端页面中实现；starter 只提供运行时所需的底层表模型、Repository、通道适配和对账补偿能力。
5. 兜底消费先告警并补发到原通道，不绕过 Redis/RabbitMQ 直接调用业务消费方法。
6. 消费幂等由两层共同保证：starter 负责 `messageId + consumerCode` 去重，业务方负责自身业务副作用幂等。
7. 超过最大补发或消费重试次数后进入 `FAILED_FINAL`，停止自动补偿并持续告警，等待人工处理。
8. 消息表提供配置化清理任务，按状态与保留天数清理成功链路数据，失败终态数据默认长期保留或人工归档。

## 3. 职责边界

消息链路需要拆成“架构层运行时能力”和“业务管理能力”两类，不应全部塞进 `df-message-starter`。

### 3.1 df-message-starter 负责什么

`df-message-starter` 是底层基础设施 starter，只封装跨服务复用的运行时能力：

1. 统一发送入口：`DfMessageTemplate`。
2. 发送主账本、消费账本、补发任务、告警事件等运行时表模型与 Repository。
3. Redis Stream / RabbitMQ 通道抽象与投递适配。
4. 消费入口的统一拦截、消费记录写入、业务监听调用和结果回写。
5. Watchdog 对账能力：发送补投、消费超时识别、补发任务创建。
6. 告警 SPI：定义 `MessageAlarmNotifier` 等扩展点，允许业务侧接入钉钉、企业微信、邮件、Webhook。
7. RabbitMQ 队列治理、Redis Stream Consumer Group 创建/校验等中间件运行时动作。
8. 配置匹配与运行时读取，例如读取已发布且启用的队列配置参与消费对账。

starter 不负责：

1. 队列配置新增、修改、删除、发布、下线等管理工作流。
2. 管理端 REST Controller。
3. 前端页面。
4. 菜单、权限、角色授权、操作审计等平台管理能力。
5. 钉钉、企业微信、邮件账号维护和通知模板维护。
6. 人工补发、人工忽略、人工关闭告警等运营动作页面。

### 3.2 df-ygt-biz-base 后端负责什么

`df-ygt-biz-base` 是业务基础服务，适合承接消息链路的管理面能力：

1. 队列配置维护：新增、编辑、复制、删除草稿。
2. 队列发布与下线：校验配置完整性，更新 `queue_status` 和 `enabled` 状态。
3. 队列消费范围维护：维护 `topic_pattern`、`key_pattern`、消费者编码、消费组、队列编码。
4. 超时和兜底策略维护：维护消费超时时间、是否告警、是否兜底补发、最大重试次数等业务策略。
5. 告警策略维护：维护告警通道、接收人、静默窗口、通知模板配置，并提供 `MessageAlarmNotifier` 实现 Bean。
6. 消息运维查询：查询发送账本、消费账本、补发任务、告警事件。
7. 人工运维动作：人工补发、终止补发、重新打开失败终态、关闭告警、标记人工处理。
8. 权限和审计：接入医共体平台菜单、角色、权限和操作日志。

`df-ygt-biz-base` 可以依赖 `df-message-starter` 暴露的实体、Repository 或底层 Service，但业务工作流应在自身领域包内封装，不反向沉入 starter。

### 3.3 前端页面负责什么

前端页面只属于管理面，不属于 starter：

1. 队列配置列表、详情、编辑、复制。
2. 发布、下线、启用、停用、删除草稿等按钮动作。
3. topic/key 匹配预览和影响消费者预览。
4. 发送记录、消费记录、补发记录、告警记录查询。
5. 人工补发、关闭告警、查看错误堆栈。
6. 告警通道、接收人、模板配置维护。

### 3.4 分层原则

1. starter 提供“机制”，业务基础服务提供“管理流程”。
2. starter 可以定义运行时数据契约，但不做管理端业务编排。
3. starter 的 API 应保持低侵入、可被多个业务服务复用。
4. `df-ygt-biz-base` 可以把 starter 的运行时数据包装成业务管理接口和页面模型。
5. 后续若其他业务线也要管理消息配置，应复用 `df-ygt-biz-base` 的服务能力或抽取独立管理服务，而不是把 Controller 和页面逻辑下沉到 starter。

## 4. 总体链路

```text
业务服务调用 DfMessageTemplate.publish
        ↓
写入 df_message_send，状态 WAIT_SEND
        ↓
业务事务提交后投递到当前全局通道
        ↓
Redis Stream / RabbitMQ 接收消息
        ↓
消费入口写入或锁定 df_message_consume
        ↓
执行业务监听方法
        ↓
消费成功写 CONSUMED，失败写 CONSUME_FAILED / WAIT_RETRY
        ↓
Watchdog 定时对账发送表、队列配置表、消费表
        ↓
发现超时未消费或失败终态时写告警、补发任务并投递原通道
```

## 5. 核心数据表

### 5.1 df_message_send

发送主账本。每次业务发布消息都必须先写入该表。

关键字段：

1. `message_id`：全链路消息 ID。
2. `topic`：消息主题。
3. `route_key`：路由键。
4. `message_key`：业务唯一键。
5. `payload_json`：消息体 JSON。
6. `payload_type`：消息体 Java 类型。
7. `headers_json`：消息头 JSON。
8. `channel_mode`：投递通道，`REDIS` 或 `RABBITMQ`。
9. `send_status`：发送状态。
10. `send_attempts`：发送尝试次数。
11. `next_retry_time`：下一次补投时间。
12. `sent_time`：发送成功时间。
13. `last_error`：最后一次错误信息。
14. `source_application`：来源应用名。

发送状态建议：

1. `WAIT_SEND`：等待发送。
2. `SENDING`：发送中。
3. `SENT`：已发送。
4. `WAIT_RETRY`：等待重试。
5. `SEND_FAILED`：发送失败。
6. `FAILED_FINAL`：失败终态。

### 5.2 df_message_consume

消费账本。每个消费者处理每条消息都必须有记录。

关键字段：

1. `message_id`：消息 ID。
2. `consumer_code`：消费者编码。
3. `consumer_group`：消费组。
4. `queue_code`：队列编码。
5. `topic`：消息主题。
6. `message_key`：业务唯一键。
7. `consume_status`：消费状态。
8. `consume_attempts`：消费尝试次数。
9. `received_time`：收到消息时间。
10. `consume_start_time`：消费开始时间。
11. `consume_done_time`：消费完成时间。
12. `instance_id`：消费实例 ID。
13. `last_error`：最后一次错误信息。

唯一约束：`message_id + consumer_code`。该约束是 starter 层去重的核心。

消费状态建议：

1. `RECEIVED`：已接收。
2. `CONSUMING`：消费中。
3. `CONSUMED`：消费成功。
4. `WAIT_RETRY`：等待重试。
5. `CONSUME_FAILED`：消费失败。
6. `FAILED_FINAL`：失败终态。

### 5.3 df_message_queue_config

队列/消费者配置表。用于声明哪些队列会消费哪些 topic/key。

该表是运行时对账契约。表结构与 Repository 可由 starter 提供，但配置维护、发布、下线、权限审计和页面交互由 `df-ygt-biz-base` 承接。

关键字段：

1. `queue_code`：队列编码。
2. `consumer_code`：消费者编码。
3. `consumer_group`：消费组。
4. `topic_pattern`：主题匹配表达式。
5. `key_pattern`：路由键匹配表达式。
6. `queue_status`：`DRAFT`、`PUBLISHED`、`DISABLED`。
7. `enabled`：是否启用。
8. `fallback_enabled`：是否启用兜底补发。
9. `alarm_enabled`：是否启用告警。
10. `timeout_seconds`：该队列消费超时秒数。
11. `alarm_channels`：告警通道列表。

只有 `PUBLISHED + enabled=true` 的配置才参与实际消费、未及时消费判定和兜底补发。

### 5.4 df_message_redelivery

补发任务表。Watchdog 发现需要兜底时先创建补发任务，再由补发执行器投递到原通道。

关键字段：`message_id`、`consumer_code`、`queue_code`、`redelivery_reason`、`redelivery_status`、`redelivery_attempts`、`next_redelivery_time`、`last_error`。

### 5.5 df_message_alarm

告警事件表。告警先落库，再调用通知通道。通知失败不得影响补发任务创建。

关键字段：`alarm_type`、`message_id`、`consumer_code`、`queue_code`、`alarm_status`、`alarm_channels`、`alarm_time`、`last_error`。

## 6. Redis Stream 队列语义

Redis 模式要求 Redis 5.0+，第一版只使用 Stream + Consumer Group。

映射规则：

1. `topic/key` 映射为 Stream Key。
2. `queue_code` 或 `consumer_group` 映射为 Consumer Group。
3. 同一个 Consumer Group 下多个实例竞争消费，一条消息只由一个实例处理。
4. 一个广播消息需要被多个队列消费时，在同一个 Stream 上维护多个 Consumer Group，每个 Group 都会收到该消息一次。
5. 消费成功后执行 `XACK`。
6. 新发布队列默认从 `$` 开始消费后续消息，历史消息是否补发由数据库补发任务显式控制。

不采用 Pub/Sub 的原因：Pub/Sub 没有持久化、ACK、Pending、Consumer Group，消费者离线时会丢消息，无法承载本方案的消费对账和补偿语义。

## 7. RabbitMQ 队列语义

RabbitMQ 模式继续复用 Spring AMQP 能力：

1. 自动声明 exchange、queue、binding。
2. 支持 topic/direct exchange。
3. 队列名优先使用 `queue_code`，未指定时按应用名、topic、key 生成。
4. 同一队列多实例共享消费，保证同一队列内一条消息只被一个实例处理。
5. RabbitMQ Management API 继续用于 lazy queue、max-in-memory-* 等治理策略。

## 8. 未及时消费判定

判定不依赖 Redis/RabbitMQ 队列长度，而依赖数据库三方对账：

1. 从发送表查询 `send_status=SENT` 且 `sent_time <= now - timeout` 的消息。
2. 根据消息的 `topic/key` 查询 `PUBLISHED + enabled=true` 的队列配置。
3. 对每个期望消费者查询消费表是否存在 `message_id + consumer_code + CONSUMED`。
4. 不存在成功消费记录时，判定该消费者未及时消费。
5. 若该队列启用告警，则写入告警事件。
6. 若该队列启用兜底，则创建补发任务。

示例：主索引消息发出后，配置表维护了 3 个队列会消费该消息。5 分钟后发送表存在该消息，但消费表只有 2 个消费者成功记录，则缺失的第 3 个消费者触发告警与补发。

## 9. 定时兜底任务

Watchdog 至少包含三类任务：

1. 发送补投：扫描 `WAIT_SEND`、`SEND_FAILED`、`WAIT_RETRY` 且到达 `next_retry_time` 的消息，重新投递原通道。
2. 消费超时对账：扫描已发送但缺失消费成功记录的消息，生成告警与补发任务。
3. 补发执行：扫描到期补发任务，重新投递原消息到原 topic/key。

第一版可基于 Spring `@Scheduled` 实现，并预留接口，后续可替换为 XXL-JOB、Quartz 或平台调度中心。

## 10. 告警扩展

starter 提供 `MessageAlarmNotifier` SPI：

```java
public interface MessageAlarmNotifier {
    boolean supports(String channel);
    void send(MessageAlarmNotice notice);
}
```

第一版内置日志型 notifier 作为兜底。钉钉、企业微信、邮件、Webhook 由业务侧或后续独立 starter 提供实现 Bean，避免主 starter 过早绑定第三方 SDK。
