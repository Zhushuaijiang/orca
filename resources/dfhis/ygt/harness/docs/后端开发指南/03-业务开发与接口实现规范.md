# 业务开发与接口实现规范

## 1. 文档定位

本文档是医共体业务微服务在代码实现阶段必须长期遵守的业务实现规范，负责回答以下问题：

1. 实体字段怎么命名、怎么写中文注释。
2. 业务代码目录怎样组织。
3. 接口应如何设计，HTTP 方法怎样使用。
4. DTO、批量增删改、技术主键、OpenAPI 声明应怎样落地。
5. Controller、Service、Entity、Repository、分页等实现模板应该是什么风格。

## 2. 实体与模型规范

### 2.1 JPA 实体中文注释规范

1. 所有 JPA 实体类字段必须增加中文注释。
2. 注释必须直接描述字段业务语义，不能写无意义注释。
3. 标准字段同样必须写注释，包括创建人、创建时间、修改人、修改时间；若数据库 DDL 保留 `tenantid` 列，也必须为该列补齐中文注释。
4. 新增实体、修改实体字段时，注释必须与字段保持同步更新。

示例：

```java
@Column(name = "jigoumc", length = 200, nullable = false)
// 机构名称
private String jiGouMc;
```

### 2.2 实体字段命名规范

1. 实体类字段名按拼音驼峰创建，不直接使用数据库小写列名作为 Java 字段名。
2. 一般情况下采用“前两个拼音全拼 + 后续拼音首字母”的规则。
3. 数据库列名继续保持数据库设计规范，不受 Java 字段命名方式影响，统一通过 @Column(name = "...") 映射。
4. 遇到约定俗成的特殊字段，可按可读性优先处理，但必须统一风格，不能同一项目中混用多套规则。

示例：

1. 机构名称 -> jiGouMc
2. 机构代码 -> jiGouDm
3. 上级机构ID -> shangJiJgId
4. 创建人 -> chuangJianRen
5. 修改人 -> xiuGaiRen

### 2.3 特殊字段约束

如业务实体需自行声明以下标准字段，固定命名如下：

1. 创建人固定使用 chuangJianRen
2. 修改人固定使用 xiuGaiRen
3. 不再要求业务实体显式声明租户字段；租户列命名统一在数据库 DDL 中保留为 `tenantid`

关于时间字段，统一处理如下：

1. 若实体直接继承 BaseEntity 且复用其审计字段，则以 BaseEntity 现有字段为准，不重复声明第二套创建时间、修改时间字段。
2. 若因既有库表或业务建模约束，需要在实体中显式声明对应业务审计时间字段，则固定使用 chuangJianSj、xiuGaiSj。
3. 禁止在同一服务内混用多套时间字段命名表达同一层语义。

关于租户字段，统一处理如下：

1. 业务实体 **不要** 因为数据库里存在 `tenantid` 列就额外声明 `tenantId` 字段。当前框架内部若在 BaseEntity 中保留只读 `tenantId` 映射，仅用于查询回填与基础设施兼容，不代表业务建模时需要显式体现该字段。
2. 业务代码 **禁止** 调用 `setTenantId(...)`、`getTenantId()` 后再自行参与业务分支判断、在 DTO/Request 中接收 tenantId、在 JPQL/Criteria/Specification 中手写 `tenantId = ?` 条件。普通 CRUD、查询、保存、更新、删除逻辑一律把 tenantId 当作框架托管字段，不允许开发人员显式 get / set。
3. 框架会在 Hibernate `StatementInspector` 阶段统一改写 SQL：
   - INSERT：自动追加 `tenantid` 列与当前租户值；
   - UPDATE / DELETE / SELECT：自动在 WHERE 中追加 `表别名.tenantid = ?`，含 JOIN、子查询、CTE。
4. 当前租户 ID 由 `df-core-starter#RequestContextFilter` 从 `TenantId` 请求头写入 `RequestContextHolder`；缺失时使用默认 `0`。如需在异步任务、消息消费者、基础设施扩展中显式传递租户，统一通过 `RequestContextHolder` API，不要再使用旧的 `TenantContext`（已 @Deprecated）。
5. 所有受租户隔离的业务表在 DDL 中 **必须** 保留 `tenantid` 列，且默认值固定为字符 `0`；禁止把该列定义为“无默认值”或继续沿用“允许为空”的旧方案。推荐写法：`tenantid varchar(64) not null default '0'`。
6. 若个别表确实不需要租户隔离（如全局字典、平台级配置），通过 `df.jpa.tenant.ignore-tables` 配置忽略，不要在实体上做特殊处理。

标准 DDL 模板如下，新增业务表默认按此模式落地：

```sql
create table yi_liao_ji_gou (
    zhujianid varchar(64) not null comment '主键ID',
    jiGouMc varchar(200) not null comment '机构名称',
    jiGouDm varchar(64) default null comment '机构代码，按YGT+6位行政区划+机构类型码+3位序号生成，对应第三方接口YiLiaoJGDM',
    chuangJianSj datetime not null default current_timestamp comment '创建时间',
    xiuGaiSj datetime not null default current_timestamp on update current_timestamp comment '修改时间',
    tenantid varchar(64) not null default '0' comment '租户ID',
    primary key (zhujianid),
    key idx_yi_liao_ji_gou_tenantid (tenantid)
) comment='医疗机构';
```

模板约束：

1. `tenantid` 必须出现在表结构中，且默认值必须是字符 `0`，不要写成 `0` 数字、`null`、`default null` 或空字符串。
2. 受租户隔离的业务表建议为 `tenantid` 建普通索引，避免自动注入租户条件后出现全表扫描。
3. 初始化 SQL、示例 SQL、修复 SQL 若未特别说明租户值，统一使用字符 `0`。
4. 业务实体生成时不要因为 DDL 中存在 `tenantid` 就主动补一个 `tenantId` 字段；数据库列名保持 `tenantid`，若框架基类内部已有只读映射则直接沿用，不要在业务模型里重复声明。

### 2.4 医共体机构编码规范

医共体机构主档的机构代码统一按平台规则生成，不允许页面或外部调用方手填：

1. `jiGouDm` / `jigoudm` 固定格式为 `YGT` + 6位国标行政区划代码 + 1位机构类型码 + 3位序号，例如 `YGT330106H001`。
2. 6位行政区划代码当前由 `jiGouSsx` / `jigoussx` 承载，必须是 6 位数字，不再保存省市区中文地址文本；前端/接口可不传，服务端保存时优先取入参，入参为空则取系统参数 `公用_医共体行政区划代码`，最终仍以 6 位代码落库。
3. `jiGouLb` / `jigoulb` 是机构类型码，保存机构时必填，必须使用大写字母字典：`H` 医院、`C` 社区卫生服务中心、`T` 乡镇卫生院、`Z` 诊所/卫生室、`Y` 妇幼保健院、`J` 疾控中心、`G` 监管机构。
4. 新增机构时后端按同一行政区划和机构类型码下的最大 3 位序号递增生成机构代码；修改行政区划或机构类型码时，后端重新按新前缀生成机构代码。
5. 对外标准字段如 `YiLiaoJGDM` 必须取机构代码 `jiGouDm`，不得使用平台结构 ID `jiGouId`。
6. 机构登记号使用 `jiGouDjh` / `jigoudjh`，由原 `jigoubzdm` 字段更名而来；医保机构编码使用 `yiBaoJgDm` / `yibaojgdm`。

### 2.5 技术主键与业务唯一性

1. 涉及多字段业务唯一键的表，数据库设计仍统一增加 zhujianid 作为技术主键。
2. 业务唯一性通过业务校验和数据库约束承接，不再直接采用复合主键映射。
3. 数据库列名 `tenantid` 与框架内部只读映射字段 `tenantId` 必须明确区分，不得混淆命名层次。

## 3. 领域目录与包结构规范

1. 机构、组织、科室、人员等相近业务模块，在代码目录上统一归档到 domain/org 父域，再按具体子域拆分。
2. 不允许将组织域相关能力平铺散落在多个无关联的同级包下。

## 4. 接口设计规范

### 4.1 HTTP 方法基线

1. 接口整体遵循 RESTful 风格。
2. 项目内统一只使用 GET 和 POST 两种 HTTP 方法。
3. 查询类接口默认优先使用 GET。
4. 当查询条件复杂且不适合通过 path/query 参数表达时，可使用 POST 查询，但必须在接口声明中说明原因与约束。
5. 新增、修改、删除、批量新增、批量修改、批量删除、批量混合增删改统一使用 POST，不再单独启用 PUT 和 DELETE。

### 4.2 路径设计规范

1. 业务 Controller 的类级 `@RequestMapping` 必须使用固定字面量路径，不通过变量拼接注册接口路径。
2. 业务接口统一采用 `/api/业务域/资源名` 结构，业务域按模块归属取值，例如 `/api/sys`、`/api/org`、`/api/base`。
3. 不允许在业务 Controller 中写成 `/api/{spring.application.name}` 或 `/api/${spring.application.name}`，接口路径不携带服务名。
4. 不允许通过 `server.servlet.context-path` 实现业务接口前缀；该配置会同步影响 Swagger、OpenAPI 文档、Actuator 健康检查等非业务端点。
5. Swagger、OpenAPI、Actuator 端点应保持框架默认或平台统一配置，不应被业务接口前缀规则连带改动。
6. 接口路径尽量通过资源分级表达语义，而不是堆砌动作缩写。
7. 不推荐无层级的平铺式命名。
8. 设计增删改查接口时，优先参考当前仓库 demos 目录和脚手架已存在实现，不允许脱离既有模式另起一套风格。

建议示例：

1. `@RequestMapping("/api/org/jigou")`
2. GET /api/org/jigou/{jiGouId}
3. GET /api/org/jigou/page
4. POST /api/org/jigou/save
5. POST /api/org/jigou/remove
6. POST /api/org/jigou/save-list

## 5. DTO 与批量增删改规范

### 5.1 DTO 基类要求

1. 业务 DTO 优先继承 com.df.utility.dto.DTOBase。
2. DTO 入参和出参优先使用脚手架已有基础类与约定。

### 5.2 单条与批量处理模式

1. 单条新增或修改时，通过 DTOState 区分 New、Update、UnChange。
2. 若批量接口存在删除动作，必须在团队统一 DTOState 删除态语义后再落地实现，不允许各模块自行发明删除表达方式。
3. 批量接口统一接收 List<DTO_XXX>。
4. 批量接口内部按 DTOState 对新增、修改、删除数据分组处理。
5. 后续同类基础数据、字典、机构、组织、人员等增删改查接口，默认沿用这一模式开发，除非有明确例外约束。

## 6. 主键、转换与已有模式复用规范

1. 业务主键如采用字符串雪花 ID，优先使用 SequenceUtil。
2. 遇到 demos 目录、脚手架模块中已存在的 DTO、工具类、批量增删改模式时，优先复用，不再按通用 Spring 习惯自由发挥。
3. 实体与 DTO 之间的常规字段映射，优先复用 ConverterUtil，不再单独创建 Mapper 类。

## 7. API 文档规范

### 7.1 强制要求

1. 所有业务服务开发都必须遵从脚手架 API 文档规范，接口 API 声明是标配，不是可选项。
2. 所有新增或修改的对外 REST 接口，都必须补齐 OpenAPI 注解。
3. 新增、修改、下线接口时，API 声明与业务代码必须同步提交。
4. 未达到 API 声明要求的接口，视为未完成开发，不应进入联调、测试验收或 PR 合并。

### 7.2 最低注解要求

至少包含：

1. @Tag
2. @Operation
3. 关键参数说明
4. 请求体 @Schema
5. DTO、请求体、响应体字段的 @Schema 业务语义描述
6. 主要响应码声明

### 7.3 必须显式写出的调用约束

需要以下约束的接口，必须在 API 声明中明确写出，不允许只靠调用方口头约定：

1. TenantId
2. Authorization
3. 分页参数
4. 幂等参数
5. 其他关键调用前置条件

## 8. 标准代码模板

### 8.1 Controller 模板

```java
@RestController
@RequestMapping("/api/base/patients")
public class PatientController {

    private final PatientService patientService;

    public PatientController(PatientService patientService) {
        this.patientService = patientService;
    }

    @GetMapping("/{id}")
    public PatientDetailResponse getById(@PathVariable String id) {
        return patientService.getById(id);
    }

    @PostMapping
    public String create(@Valid @RequestBody CreatePatientRequest request) {
        patientService.create(request);
        return "OK";
    }
}
```

说明：

1. Controller 类级路径必须使用固定字面量 `/api/业务域/资源名`，不要通过变量拼接注册接口路径。
2. 业务域必须与模块归属一致，例如系统域使用 `/api/sys/...`，组织域使用 `/api/org/...`，基础资料域使用 `/api/base/...`。
3. 业务接口路径不得携带服务名，也不得通过 `server.servlet.context-path` 配置实现，避免 Swagger、OpenAPI 文档和 Actuator 健康检查路径被连带改变。
4. 方法直接返回业务对象或字符串即可，df-core-starter 会统一包装成 R<T>。
5. 若业务明确想手工控制返回值，也可以直接返回 R<T>，但不要混用多种返回协议。

### 8.2 Service 模板

```java
@Service
public class PatientService {

    private final PatientRepository patientRepository;

    public PatientService(PatientRepository patientRepository) {
        this.patientRepository = patientRepository;
    }

    public PatientDetailResponse getById(String id) {
        Patient patient = patientRepository.findById(id)
                .orElseThrow(() -> new BusinessException(CommonErrorCode.NOT_FOUND, "患者不存在"));
        return new PatientDetailResponse(patient.getId(), patient.getName());
    }

    public void create(CreatePatientRequest request) {
        Patient patient = new Patient();
        patient.setName(request.name());
        patientRepository.save(patient);
    }
}
```

### 8.3 Entity 模板

```java
@Entity
@Table(name = "patient")
public class Patient extends BaseEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    @Column(name = "zhujianid", nullable = false, length = 64)
    private String id;

    @Column(nullable = false)
    // 患者姓名
    private String name;

    public String getId() {
        return id;
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
        touch();
    }
}
```

说明：

1. BaseEntity 当前只保留审计字段与 tenantId 只读映射，业务实体必须自行声明 `@Id` 主键字段。
2. 业务表主键列默认按 DDL 规范映射到 `zhujianid`，Java 属性名可继续使用 `id`。

### 8.4 Querydsl Q 类型模板

```java
public class QPatient extends EntityPathBase<Patient> {

    public static final QPatient patient = new QPatient("patient");

    public final StringPath id = createString("id");
    public final StringPath tenantId = createString("tenantId");
    public final StringPath name = createString("name");
    public final NumberPath<Integer> age = createNumber("age", Integer.class);

    public QPatient(String variable) {
        super(Patient.class, forVariable(variable));
    }
}
```

说明：

1. 这是最小化模板，目的是让 df-jpa-starter 能完成仓储初始化。
2. 正式项目应优先使用 APT 自动生成，不建议长期手写维护复杂实体的 Q 类型。

### 8.5 Repository 模板

```java
public interface PatientRepository extends BaseRepository<Patient, String> {

    Optional<Patient> findByName(String name);

    @MaxRowLimit(100)
    List<Patient> findByNameContaining(String keyword);
}
```

### 8.6 分页查询模板

```java
public PageData<PatientDetailResponse> queryPage(int pageNumber, int pageSize) {
    Pageable pageable = PageRequest.of(pageNumber, pageSize, Sort.by("createdAt").descending());
    return patientRepository.queryPageData(null, pageable, patient ->
            new PatientDetailResponse(patient.getId(), patient.getName()));
}
```

说明：

1. 若实体直接复用 BaseEntity 审计字段，分页排序字段应按 BaseEntity 实际字段命名使用。
2. 不允许在同一服务中同时把 createdAt 和 chuangJianSj 当作同层语义字段混用。

## 9. 日志实现规范

### 9.1 配置文件与命名要求

1. 业务服务如需在 Logback 中读取 `spring.application.name`、环境变量或 Spring 配置，必须使用 `logback-spring.xml`，不要误用普通 `logback.xml`。
2. 日志服务名统一从 `spring.application.name` 派生，推荐使用 `springProperty` 映射为 `APP_NAME` 后再用于 `contextName`、日志文件名、滚动文件名。
3. 示例工程、复制模板、脚手架交付物中，不允许保留 `{服务名}.log` 这类占位符文本，必须改成可直接运行的标准写法。

### 9.2 输出与滚动基线

1. 常规业务服务至少输出控制台日志、应用主日志、错误日志三条链路；除明确规划独立 trace 链路外，不额外拆分高噪声日志文件。
2. 主日志文件统一记录 `INFO` 及以上的常规运行日志；错误日志文件只保留 `ERROR` 级别，避免问题排查时混入大量无关信息。
3. 文件日志统一采用按时间加按大小滚动，并保留有限历史；禁止长期使用“只按天切分、不限单文件大小”或“完全不滚动”的配置。
4. 日志 pattern 可输出 `%X{traceId}` 等 MDC 字段，但前提是上下文里已存在对应值；不要为了 pattern 中的链路标识引入额外厂商依赖。

### 9.3 禁止项

1. 通用 starter、示例工程、业务模板中禁止直接依赖 SkyWalking 专用 Logback Layout 或其他 APM 厂商日志类，除非该依赖是明确选型、已接入、已文档化的正式基线。
2. 禁止把历史项目中的包名级 logger 配置直接复制到新服务模板，例如与当前服务无关的 `com.xxx.xxx` 定向 logger。
3. 禁止在业务代码中使用 `System.out.println`、`printStackTrace()` 或手工拼接大段调试字符串替代正式日志。
4. 禁止在日志中输出密码、token、密钥、身份证号、手机号全量等敏感信息；必要时必须做脱敏或摘要化处理。

### 9.4 业务代码记录要求

1. Controller、Service、消息监听器、定时任务统一通过 SLF4J 记录日志，不再自造日志门面。
2. `INFO` 级别用于关键业务节点和状态变化，`ERROR` 级别用于必须进入告警或排障链路的失败场景，`DEBUG` / `TRACE` 只用于短期调试或独立观测链路。
3. 记录异常日志时应保留异常对象，避免只打印 `exception.getMessage()` 导致堆栈丢失。
4. 若确需增加局部高噪声日志，必须说明用途、范围和关闭方式，避免默认常驻在主日志链路中。
5. 需要观测接口入参/出参时，优先复用 `df-core-starter` 的统一 HTTP 日志能力，不要在 Controller 中重复手写请求/响应打印逻辑。
6. 总开关 `df.core.web.logging.enabled` 默认开启，摘要日志默认记录 URL、headers、query、客户端地址、状态码和执行时间；不要再单独引入历史 `HttpTraceRepository` 风格的请求计时实现。
7. 接口 body 打印统一通过 `df.core.web.logging.body-path-patterns` 按路径开启；建议将该配置放入服务专属 Nacos，由配置中心动态增删需要观测的接口，不要把临时调试路径硬编码进业务代码。
8. 默认请求头日志会输出 headers，但敏感头必须按名称脱敏；命中 body 日志的接口仍需做敏感字段治理，如 DTO 包含身份证号、手机号、token、密码、密钥、影像地址等内容，必须在进入正式日志前脱敏、裁剪或改为摘要输出。

## 10. 开发自查清单

1. 实体字段是否补齐中文业务注释。
2. Java 字段命名是否符合拼音驼峰规则。
3. 组织域模块是否归档到 domain/org。
4. 查询接口是否优先使用 GET，非 GET 查询是否有明确理由。
5. 新增、修改、删除、批量接口是否统一使用 POST。
6. Controller 类级 `@RequestMapping` 是否统一使用固定字面量 `/api/业务域/资源名`，是否避免使用服务名占位符、变量拼接或 `server.servlet.context-path` 实现业务前缀。
7. DTO 是否复用 DTOBase，批量接口是否统一接收 List<DTO_XXX>。
8. 主键、转换、批量模式是否复用既有 SequenceUtil、ConverterUtil 和 demos 模式。
9. 是否为所有对外接口补齐了 OpenAPI 注解和字段级 Schema 描述。
10. 代码实现变化后，是否同步更新本规范与相关主文档。

## 11. 最终原则

后续接口开发前，先以 01、02、03 为准，不再临时决定风格。若代码实现已调整但规范文件未同步，视为任务未完成。
