# 基础能力复用与架构红线

## 1. 文档定位

本文档是医共体业务微服务的基础能力复用红线，负责回答以下问题：

1. 哪些能力必须复用脚手架，不能在业务服务里重造。
2. 统一响应、统一异常、错误码、Trace、租户头、上下文对象的权威约定是什么。
3. JPA、Redis、JWT、消息、动态数据源等基础设施在业务服务中的正确使用边界是什么。
4. 哪些实现方式属于明确禁止事项。

本文档不负责服务接入步骤、配置中心基线和实体/接口实现细节；这些内容分别以 01 和 03 为准。

## 2. 架构边界红线

1. 服务模块只能实现业务，不允许在业务模块重建基础设施层。
2. 脚手架已提供的能力必须优先复用，不允许“先自己写一版，再说后续抽公共”。
3. 业务项目不能把脚手架中的基础类复制到本服务继续维护。
4. 业务服务的自由度只存在于业务领域实现，不存在于脚手架级基类、协议和公共基础设施设计。
5. 若脚手架能力不足，优先提出“扩展脚手架”的方案，而不是在服务内复制实现。

## 3. 必须复用的基础能力清单

以下能力属于脚手架统一底座，业务服务必须复用，不得自造第二套：

1. 统一响应体：R<T>
2. 统一异常：BusinessException
3. 统一错误码：ErrorCode / CommonErrorCode
4. DTO 状态跟踪基类：DTOBase
5. 分布式唯一 ID：SequenceUtil 或其后续统一封装
6. Trace 上下文：TraceContext、RequestContext、RequestContextHolder
7. JPA 公共基类与仓储：BaseEntity、BaseRepository
8. Redis 锁与常用 Redis 操作：RedisLockUtil、RedisUtil
9. 消息发布与 routeKey 监听：MessagePublishTemplate、@DfMessageRouteKeyListener
10. 动态数据源切换：@DS 与 df-dynamic-starter
11. DTO 与实体常规转换：ConverterUtil
12. 健康检查与管理端点：df-core-starter 内置 Spring Boot Actuator
13. Web 容器优雅停机：Spring Boot 4 默认 graceful shutdown 与 `spring.lifecycle.timeout-per-shutdown-phase`

## 4. 统一协议红线

### 4.1 返回体规范

1. Controller 对外返回必须统一遵循 R<T> 协议。
2. 普通 @RestController 返回值会由 df-core-starter 自动包装成 R<T>。
3. 返回 String 时也会包装为 R.ok(...) 后再序列化。
4. 返回 R<?> 时不会重复包装。
5. 返回 ProblemDetail、ErrorResponse、Resource、byte[] 时不做二次包装。
6. `/actuator/**` 管理端点保持 Spring Boot Actuator 原生响应，不参与 R<T> 自动包装。

禁止事项：

1. 禁止项目内部再定义第二套 Result、Response、ApiResult、CommonResponse 等通用响应壳。
2. 禁止手写第二个 ResponseBodyAdvice 去覆盖统一响应协议。
3. 文件下载、二进制流、原始资源类响应属于例外，但必须明确接口用途。

### 4.2 异常规范

1. 业务异常必须优先使用 BusinessException。
2. 接入 df-core-starter 后，BusinessException、参数绑定异常、参数校验异常、缺少请求参数异常、参数类型不匹配异常、请求体不可读异常、请求方法不允许异常及其他未捕获异常，都会统一转换为 R<Void>。

禁止事项：

1. 禁止在 Controller 中手写 try/catch 拼装错误 JSON。
2. 禁止把业务失败直接返回 200 + false 这类非统一语义结构。
3. 禁止新增第二套通用异常基类替代 BusinessException。

### 4.3 错误码规范

1. 优先复用 CommonErrorCode。
2. 业务扩展错误码时，必须遵循既有码段语义，不允许随意定义无规律整数。
3. 同一类错误在不同服务中必须保持一致的 code/msg 语义。

禁止事项：

1. 禁止新增第二套公共错误码枚举并与 CommonErrorCode 并行漂移。

### 4.4 Trace 与租户头规范

统一约定如下：

1. 系统统一链路头为 TraceId。
2. 多租户统一请求头为 TenantId。
3. 灰度调用统一请求头为 GrayTag 与 GrayScopes，不使用额外 X 前缀。
4. 入站请求会读取 TraceId；如无值，系统自动生成；响应头会回写 TraceId。
5. 接入 df-cloud-starter 后，通过 RestClient 发起的下游调用会自动透传 TraceId、GrayTag 与 GrayScopes。

禁止事项：

1. 禁止新增第二套 Trace 头或第二套路由追踪约定。
2. 禁止新增第二套租户头命名。
3. 禁止不同项目各自定义不同的租户 Header。
4. 禁止新增第二套灰度调用 Header 命名，禁止使用带 X 前缀的灰度头约定。
5. 异步任务、远程调用、审计日志若依赖租户信息，需要显式传递上下文，不能假设 ThreadLocal 会自动跨线程传播。

### 4.5 健康检查与管理端点规范

1. 接入 df-core-starter 后，健康检查与管理端点统一复用 Spring Boot Actuator。
2. 默认 Web 暴露范围仅包含 `/actuator/health`，用于存活探针、就绪检查和基础连通性验证。
3. 如网关或监控平台需要聚合版本信息，业务服务应显式配置 `management.endpoints.web.exposure.include=health,info`。
4. `/actuator/**` 响应保持 Actuator 原生结构，不走 R<T> 包装，以保证探针、网关和监控组件可以按 Spring Boot 标准格式识别。
5. 生产环境不得直接暴露全部端点；`env`、`configprops`、`beans`、`heapdump` 等敏感端点默认不应对业务网络开放。

禁止事项：

1. 禁止业务服务自行实现第二套 `/health`、`/actuator/health` 或通用健康检查控制器来替代 Actuator。
2. 禁止把 Actuator 响应强制包装成 R<T>。
3. 禁止在未配访问控制的生产环境开放 `management.endpoints.web.exposure.include=*`。

### 4.6 应用停机与生命周期规范

1. Spring Boot 4 默认启用 Web 容器优雅停机，业务服务统一复用该基线能力。
2. 停机时，内嵌 Web 容器停止接收新请求，并允许已经进入处理流程的请求在 `spring.lifecycle.timeout-per-shutdown-phase` 时间内完成。
3. 停机等待时间属于服务专属运行配置，默认使用 Spring Boot 的 `30s`；确有长接口或外部系统同步场景时，可在服务专属 Nacos 配置中调整。
4. HTTP 优雅停机不等于后台任务全部自动收尾；RabbitMQ 消费、定时任务、异步线程池、长事务等仍需按对应组件的生命周期能力单独治理。

禁止事项：

1. 禁止从旧 demo 迁移 `GracefulShutdownConfig` 之类的手工优雅停机配置。
2. 禁止自行注册 `TomcatConnectorCustomizer`、暂停 Connector、轮询 Tomcat 线程池等方式替代 Spring Boot 4 默认 graceful shutdown。
3. 禁止在无明确生产要求时配置 `server.shutdown=immediate`。

## 5. 当前用户与请求上下文规范

### 5.1 统一入口

业务服务获取“当前用户”统一走 RequestContextHolder，而不是各服务自己解析 Servlet 请求、自己定义 ThreadLocal 或自己再包一层用户上下文。

可直接使用的入口：

```java
String userId = RequestContextHolder.getUserId();
String userName = RequestContextHolder.getUserName();
String tenantId = RequestContextHolder.getTenantId();
String authorization = RequestContextHolder.getAuthorization();
```

### 5.2 请求头来源约定

1. RequestContextFilter 会在 HTTP 请求入口读取请求头并写入 RequestContextHolder。
2. 当前用户 ID 统一取自 UserId。
3. 当前用户名称统一取自 UserName。
4. 当前租户统一取自 TenantId。
5. 灰度流量标记统一取自 GrayTag，灰度作用服务范围统一取自 GrayScopes。
6. 原始令牌统一取自 Authorization 请求头。

### 5.3 推荐主路径

推荐主路径如下：

1. 网关或统一鉴权层完成认证。
2. 将 UserId、UserName、TenantId 等标准头传给下游服务。
3. 业务服务统一通过 RequestContextHolder 取值。

### 5.4 例外与限制

1. 如果链路只传了 Authorization，但没有用户头透传下来，服务内不能假定 getUserId() 一定有值。
2. 在只拿到 token 的场景下，可按需调用 JwtTokenService 解析 claims，但这只是补救路径，不是推荐主路径。
3. 异步、消息消费、定时任务等非 HTTP 入口场景，默认没有当前请求上下文，不能直接假定 RequestContextHolder.getUserId() 有值。
4. 如非 HTTP 场景确需传递用户信息，应在任务投递时显式传参，或在执行前手动构造 RequestContext 并写入 RequestContextHolder。

## 6. JWT 能力边界

### 6.1 已提供能力

接入 df-core-starter 后，会自动提供 JwtTokenService，当前已支持：

1. 生成 token
2. 解析 token claims
3. 基于配置项设置 issuer、secret、expiration

### 6.2 未自动提供的能力

当前未自动提供：

1. 登录拦截器
2. 权限注解体系
3. 基于角色的授权判断

### 6.3 结论

1. df-core-starter 提供的是轻量 JWT 服务，不等于完整认证授权框架。
2. 若业务服务要求登录态校验，需要在业务项目中补自己的认证入口。
3. Token 生成与解析必须统一复用 JwtTokenService，不允许再造第二套 token 服务。

## 7. JPA 与数据访问红线

### 7.1 基类与仓储规范

1. 新增 JPA 实体默认必须继承 BaseEntity，除非确有历史兼容约束。
2. Repository 默认必须继承 BaseRepository，而不是直接继承 JpaRepository。
3. 统一 JPA 实体与 Repository 规范，不允许绕开脚手架再造第二套基类。

### 7.2 Querydsl 与 Q 类型要求

1. df-jpa-starter 当前集成了 Querydsl 仓储工厂。
2. 业务实体必须具备对应的 Querydsl Q 类型，否则仓储初始化时可能报错。
3. 正式业务项目建议通过 APT 自动生成 Q 类。
4. 仅在最小示例或临时验证场景下，才允许手写简单 Q 类型。
5. 不建议长期手写维护复杂实体的 Q 类型。

### 7.3 查询与大结果集保护

1. 查询列表时优先使用分页或安全列表方法，避免无上限查全表。
2. 分页查询、列表查询必须遵守安全查询和大结果集保护思路。
3. 不允许无约束查全表。
4. df.jpa.max-row-limit.enabled=true 时，最大行数保护才会生效。
5. 该保护主要针对 Repository 中返回 List 的查询方法。
6. 默认阈值超限时可选择 warn 或 error。
7. 可通过 @MaxRowLimit 在方法级覆盖最大行数。

## 8. 多租户上下文边界

多租户能力分布在三个层次，业务接入时必须按此约束理解：

### 8.1 上下文层（请求上下文）

1. 由 df-core-starter 的 `RequestContextFilter` 在每个请求入口从 `TenantId` 请求头读取租户值，写入 `RequestContextHolder`；缺失时使用默认 `0`。
2. 请求结束后由过滤器统一清理上下文，避免线程污染。
3. df-tenant-starter 不再注册独立的 MVC 拦截器；旧版 `TenantContext` 保留为 @Deprecated 兼容门面，所有读写都委派给 `RequestContextHolder`。`RequestContextHolder.getTenantId()` 仅用于基础设施扩展、异步上下文透传等框架级场景，不代表普通业务代码需要主动读取实体租户字段。

### 8.2 持久层（SQL 自动改写）

接入 df-jpa-starter（或 df-tenant-starter，会传递引入 df-jpa-starter）后默认开启：

1. 由 `TenantSqlRewriter` 在 Hibernate `StatementInspector` 阶段统一改写 SQL：
   - INSERT：自动追加 `tenantid` 列与当前租户值（含 `INSERT ... VALUES`、`INSERT ... ON DUPLICATE KEY UPDATE`）；
   - UPDATE / DELETE：自动在 WHERE 中追加 `表别名.tenantid = ?`；
   - SELECT：覆盖 PlainSelect / SetOperationList(UNION) / ParenthesedSelect / 子查询 / JOIN 右表 / WithItem(CTE)。
2. 业务代码 **禁止** 调用 `setTenantId(...)`、`getTenantId()` 后再自行做租户分支判断、在 DTO/Request 中接收 tenantId、在 JPQL/Specification/Querydsl 中手写 `tenantId = ?`。普通业务模块不得显式 get / set tenantId，统一交由框架托管。
3. 当前框架内部若在 BaseEntity 中保留只读 `tenantId` 映射，则该字段仅用于查询回填，不允许业务写入，也不要求业务实体显式声明同名字段。
4. 解析后的 SQL 与改写结果由 Caffeine 二级缓存复用，无需业务关心性能。
5. 所有受租户隔离的业务表在数据库 DDL 中必须保留 `tenantid` 列，且默认值固定为字符 `0`；脚手架层依赖该列存在来完成 SQL 自动注入，禁止再使用“tenantid 可为空”或“建表时省略 tenantid，后续再补列”的做法。
6. 个别全局表（字典、平台级配置）若不需要租户隔离，统一通过 `df.jpa.tenant.ignore-tables` 配置忽略，不要在实体上做特殊处理。
7. 配置开关：
   - `df.jpa.tenant.enabled`（默认 false）：关闭后 SQL 不再自动改写；
   - `df.jpa.tenant.column`（默认 `tenantid`）：租户列名；
   - `df.jpa.tenant.cache.enabled`、`df.jpa.tenant.cache.maximum-size`：解析缓存控制。
8. 业务可通过自定义 `TenantIdProvider` Bean 覆盖默认实现（默认从 `RequestContextHolder` 取值）；但这属于基础设施扩展点，不等于允许业务代码自行维护实体 tenantId。

### 8.3 边界声明

1. 当前不会自动拒绝缺失租户头的请求；是否在网关/过滤器/业务层强校验由业务项目自行决定。
2. 异步任务、消息消费者、跨线程调度若依赖租户信息，必须显式通过 `RequestContextHolder` 复制并传递上下文，不能假设 ThreadLocal 自动跨线程传播。
3. 不允许在业务侧再实现第二套租户隔离方案（如自定义 AOP 在 Service 层注入 tenantId、在 Specification 里硬编码 `tenantId = ?` 等），统一以 SQL 改写为唯一真源。

## 9. Redis、消息与动态数据源复用规范

### 9.1 Redis 规范

1. 分布式锁统一使用 RedisLockUtil。
2. 常用 Redis 操作统一使用 RedisUtil。
3. 不允许各服务再封装第二套 RedisTemplate 通用工具层替代脚手架能力。
4. RedisUtil 的装配前提是容器中存在名为 `redisTemplate` 的 Bean；RedisLockUtil 的装配前提是存在 `RedissonClient` Bean。缺少这些基础设施时，静态方法会直接抛出 `IllegalStateException`，所以业务层不能把它当作“可选能力”。
5. RedisUtil 适合做短 TTL 缓存、幂等标记、计数器、Hash/List/Set 快捷读写、频道广播；涉及 Lua、Pipeline、事务、多 key 原子编排时，直接下沉到底层 `RedisTemplate` / Redisson API，不要硬把复杂场景塞进 util。
6. Redis key 必须显式带业务域和隔离维度，至少满足 `业务域:动作或对象:tenantId:业务主键`；禁止使用 `lock:key`、`cache:data` 这类无法定位归属的模糊命名。
7. 锁 key 与缓存 key 必须分开设计，禁止同一个 key 既做分布式锁又做业务缓存。
8. 业务层调用 util 时，应把基础设施异常转换成统一业务异常，避免把 `IllegalStateException`、`RuntimeException` 原样透传到接口层。

推荐 key 规则：

1. 分布式锁：`appointment:create:<tenantId>:<scheduleCode>:<patientIdCard>`
2. 单对象缓存：`appointment:result:<tenantId>:<appointmentNo>`
3. 幂等标记：`appointment:submit:<tenantId>:<requestId>`
4. 计数器：`appointment:counter:<tenantId>:<date>`

RedisLockUtil 模板：

```java
public void createOrder(String tenantId, String orderNo) {
    String lockKey = "order:create:" + tenantId + ":" + orderNo;
    RedisLockUtil.executeWithLock(lockKey, Duration.ofSeconds(10), () -> {
        doCreateOrder(orderNo);
        return null;
    });
}
```

多锁手动控制模板：

```java
public void confirmOrder(String tenantId, String orderNo, String stockId) {
    String orderLockKey = "order:confirm:" + tenantId + ":" + orderNo;
    String stockLockKey = "stock:deduct:" + tenantId + ":" + stockId;

    RLock orderLock = null;
    RLock stockLock = null;
    try {
        orderLock = RedisLockUtil.lock(orderLockKey, 10, TimeUnit.SECONDS);
        if (!RedisLockUtil.tryLock(stockLockKey, 0, 10)) {
            throw new BusinessException(CommonErrorCode.DISTRIBUTED_LOCK_ERROR, "库存锁获取失败");
        }
        stockLock = RedisLockUtil.getLock(stockLockKey);

        doConfirmOrder(orderNo, stockId);
    } finally {
        RedisLockUtil.unlock(stockLock);
        RedisLockUtil.unlock(orderLock);
    }
}
```

RedisUtil Hash 缓存模板：

```java
public OrderCacheView cacheOrderResult(String tenantId, String orderNo, String patientName) {
    String cacheKey = "order:result:" + tenantId + ":" + orderNo;

    Map<String, Object> payload = new LinkedHashMap<>();
    payload.put("orderNo", orderNo);
    payload.put("tenantId", tenantId);
    payload.put("patientName", patientName);

    try {
        RedisUtil.hmSet(cacheKey, payload, 1800);
        long ttl = RedisUtil.getExpire(cacheKey);
        return new OrderCacheView(orderNo, tenantId, patientName, cacheKey, ttl);
    } catch (RuntimeException exception) {
        throw new BusinessException(CommonErrorCode.CACHE_ERROR, "订单缓存写入失败", exception.getMessage());
    }
}
```

组合示例：

1. 先用 RedisLockUtil 串行化高并发写操作，解决重复提交、并发扣减、重复预约等问题。
2. 当一个业务动作需要同时控制多个不同资源时，可先分别 `lock` / `tryLock`，在 `finally` 中按逆序 `unlock`，不要把多锁释放依赖藏进业务分支里。
3. 成功执行业务后，再用 RedisUtil 把结果快照写入短 TTL 缓存，供后续查询、回显、轮询接口复用。
4. 查询缓存时优先使用 `hmGet` / `getString` / `getExpire` 组合返回业务数据和剩余 TTL；若缓存为空，按业务语义转换为 `NOT_FOUND` 或 `CACHE_ERROR`，不要直接向外暴露 util 异常。

可直接照抄的完整示例见：

1. `示例工程/df-demo-integration-service/src/main/java/com/df/example/integration/appointment/service/AppointmentCommandService.java`
2. `示例工程/df-demo-integration-service/README.md`

### 9.2 消息发布与监听规范

1. 新消息链路发送统一优先使用 DfMessageTemplate。
2. 消息发送必须先写入数据库发送账本，再由 starter 在事务提交后投递到 Redis Stream 或 RabbitMQ。
3. 消费侧必须先写入或锁定消费账本，再执行业务监听逻辑。
4. Redis 模式统一要求 Redis 5.0+，第一版只使用 Stream + Consumer Group，不使用 Pub/Sub 承载消费链路。
5. RabbitMQ 模式继续支持 exchange、queue、binding 声明和队列治理。
6. 旧 MessagePublishTemplate 与 @DfMessageRouteKeyListener 仅作为兼容和低层 RabbitMQ 入口，新业务优先接入持久化链路。
7. 队列维护、配置管理、发布、下线、人工补发、关闭告警等管理面能力不得下沉到 starter，应由 `df-ygt-biz-base` 后端和对应前端页面实现。

消息发送模板：

```java
dfMessageTemplate.publish("patient", "patient.created", payload);
```

消费对账核心规则：

1. 发送表存在已发送消息。
2. 队列配置表存在已发布且启用的期望消费者。
3. 消费表缺少 messageId + consumerCode 的 CONSUMED 记录。
4. 超过队列配置或全局消费超时时间后，Watchdog 写告警事件并创建补发任务。

新监听注解模板：

```java
@Component
public class AppointmentCreatedListener {

    @DfMessageListener(
            topic = "patient",
            key = "patient.created",
            consumerCode = "appointment-created-consumer",
            consumerGroup = "appointment-service",
            queueCode = "appointment.patient.created")
    public void onMessage(AppointmentCreatedEvent event) {
        // 处理消息
    }
}
```

完整链路设计见 [05-消息消费全链路设计方案.md](05-%E6%B6%88%E6%81%AF%E6%B6%88%E8%B4%B9%E5%85%A8%E9%93%BE%E8%B7%AF%E8%AE%BE%E8%AE%A1%E6%96%B9%E6%A1%88.md)。

### 9.3 RabbitMQ 队列治理

当开启 df.message.rabbit.management.enabled=true 后，starter 会通过 RabbitMQ Management HTTP API 对监听队列下发 policy / operator-policy，用于开启 lazy queue 或限制 max-in-memory-*。

关键配置项如下：

1. df.message.rabbit.management.enabled
2. df.message.rabbit.management.base-url
3. df.message.rabbit.management.username
4. df.message.rabbit.management.password
5. df.message.rabbit.management.vhost
6. df.message.rabbit.management.policy-priority
7. df.message.rabbit.management.operator-policy-priority

### 9.4 动态数据源规范

1. 动态数据源切换统一使用 @DS。
2. 不允许再定义第二套切库注解。

## 10. DTOBase、SequenceUtil 与 ConverterUtil 规范

### 10.1 DTO 状态跟踪

1. DTO 输入输出对象中涉及实体新增、修改、删除状态跟踪、字段原值记录等场景，统一基于 DTOBase 语义展开。
2. 需要 DTO 变更跟踪时，优先复用 DTOBase，而不是自创第二套 BaseDTO。

### 10.2 分布式 ID

1. 分布式唯一 ID 生成统一基于 SequenceUtil 或其后续统一封装展开。
2. 需要雪花 ID、流水号或分布式唯一主键时，优先复用 SequenceUtil。

### 10.3 Bean 转换

1. 实体与 DTO 之间的常规字段映射，优先复用 ConverterUtil。
2. 不允许为常规 DTO 与实体转换重复新增独立 Mapper 类。

## 11. 明确禁止的事情

服务内禁止新增或复制以下类型的代码：

1. 第二套 BaseDTO、DTOBase、EntityStateTracker 一类的 DTO 基类。
2. 第二套 SequenceUtil、Snowflake、IdWorker、UidGenerator 一类的主键生成器。
3. 第二套统一响应模型，例如 ApiResult、CommonResponse、Result。
4. 第二套统一异常基类、统一错误码体系、统一上下文对象。
5. 在业务模块 comm、base、utils、support、context 中堆叠脚手架已有职责的通用实现。
6. 第二套 Trace 头或第二套租户头。
7. 第二套基础分页模型、响应模型、异常模型。
8. 绕过 starter 已有能力，自行重复实现同类基础设施。
9. 把脚手架公共能力先复制到业务模块落地，再以“后续再抽公共”为理由保留重复实现。
10. 第二套健康检查或管理端点实现，用来替代 df-core-starter 内置的 Actuator 能力。
11. 第二套 Web 容器优雅停机实现，例如旧式 `GracefulShutdownConfig`、手工 Tomcat Connector 暂停和线程池等待逻辑。

## 12. 架构自查清单

1. 是否复用了脚手架已有基类和工具，而不是新建重复实现。
2. 是否没有在业务模块新增第二套统一响应、异常、错误码、上下文、DTO 基类、ID 生成器。
3. 是否没有新增第二套 Trace 头或租户头命名。
4. 是否没有默认编写无上限 List 查询。
5. 是否正确理解了 JwtTokenService、TenantContext、RequestContextHolder、BaseRepository、@DfMessageRouteKeyListener 等能力的职责边界。
6. 是否确认健康检查统一走 `/actuator/health`，并按需显式暴露 `/actuator/info`。
7. 是否确认优雅停机复用 Spring Boot 4 默认 graceful shutdown，而不是新增旧式 `GracefulShutdownConfig`。
8. 若脚手架能力不足，是否明确选择“扩展脚手架”而非服务内旁路实现。

## 13. 最终原则

只要涉及统一响应、统一异常、统一错误码、上下文对象、ID 生成、JPA 基类、Repository 基类、Redis、消息、动态数据源、租户上下文、健康检查与管理端点等基础设施，服务团队必须优先复用脚手架，不得自行平替。
