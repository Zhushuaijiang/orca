# 接入基线与配置规范

## 1. 文档定位

本文档是医共体业务微服务接入 df-java-base 脚手架时的唯一接入基线，负责回答以下问题：

1. 业务项目应该继承哪个 parent，版本基线是什么。
2. 不同业务场景应引入哪些 starter，哪些能力只是可选能力。
3. 本项目当前认可的配置中心方案、Nacos 分层方案、配置文件边界是什么。
4. 本项目当前多租户、认证、部署引导的系统边界是什么。
5. 新服务完成接入后，最低验收条件是什么。

本文档不负责定义统一响应、异常、错误码、基础设施复用红线，也不负责实体命名、接口实现、AI 约束。这些内容分别以：

1. 02-基础能力复用与架构红线.md
2. 03-业务开发与接口实现规范.md
3. 04-AI协作与代码评审规范.md

为准。

## 2. 当前技术基线

### 2.1 版本基线

当前医共体业务微服务统一基线如下：

1. Java 25
2. Spring Boot 4.0.5
3. Spring Cloud 2025.1.1
4. 脚手架版本 4.0.0-SNAPSHOT

### 2.2 JDK 基线

1. 编译和运行默认使用 JDK 25。
2. 当前固定 JDK 25 路径为 D:\Program Files\Java\jdk-25.0.2.10-hotspot。
3. 涉及 Maven、编译、运行、IDE 配置时，优先显式使用上述 JDK，避免环境漂移。

## 3. 接入目标

业务项目接入 df-java-base，不是“引几个依赖”这么简单，而是要整体接受统一底座约束。接入后的统一目标包括：

1. 统一版本、依赖与构建信息基线。
2. 统一响应协议、异常模型、错误码和上下文约定。
3. 统一 TraceId 与租户头契约。
4. 统一 API 文档入口、OpenAPI 元数据、健康检查与管理端点基线。
5. 统一 JPA 基类、Repository 能力与大结果集保护。
6. 统一基础设施接入方式，包括 Redis、消息、动态数据源、JWT 等能力。
7. 统一配置中心分层方案和配置命名。

业务项目的自由度只存在于业务领域实现，不存在于脚手架级基类、协议和公共基础设施设计。

## 4. 依赖接入基线

### 4.1 Parent 与 BOM 规则

1. 业务项目推荐直接继承 df-parent。
2. 如业务项目已有自定义 parent，不希望替换根 parent，则必须通过 dependencyManagement 导入同版本 df-parent BOM，保证依赖版本不漂移。
3. 不允许继承 df-java-base。df-java-base 是根聚合 POM，用于统一聚合版本点、构建与制品追溯，不承载业务项目 parent 语义。
4. 子模块不得自行钉第三方依赖版本，第三方版本统一由 df-parent 管理。
5. com.df 自家模块版本必须跟随脚手架统一管理，不允许在业务服务中随意分叉。
6. 继承 df-parent 的后端服务默认继承 git-commit-id-maven-plugin 构建配置，构建产物会生成 target/classes/git.properties，字段限定为 git.branch、git.commit.id.abbrev、git.commit.time；业务 POM 不再重复声明该插件。
7. 后端应用 POM 只需声明 spring-boot-maven-plugin 启用 Boot 打包；build-info 与 excludeDevtools 配置由 df-parent 的 pluginManagement 统一管理，构建产物会生成 target/classes/META-INF/build-info.properties，业务 POM 不再重复写本地配置。

推荐 parent 写法：

```xml
<parent>
    <groupId>com.df</groupId>
    <artifactId>df-parent</artifactId>
    <version>4.0.0-SNAPSHOT</version>
</parent>
```

已有自定义 parent 时的 BOM 写法：

```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.df</groupId>
            <artifactId>df-parent</artifactId>
            <version>4.0.0-SNAPSHOT</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

### 4.2 Maven 仓库要求

业务项目本地或构建机的 Maven settings.xml 必须满足：

1. 能访问脚手架发布仓库。
2. 已配置对应 server 凭证。
3. 能解析 snapshot 版本。

### 4.3 Starter 接入矩阵

当前已落地模块与职责如下：

| 模块 | 当前已落地能力 | 接入建议 |
|------|----------------|----------|
| df-java-base | 根聚合 POM、整仓构建与发布入口 | 不作为业务项目 parent 或普通依赖 |
| df-parent | 统一版本管理、Java 25 编译基线、Boot/Cloud 依赖基线、Git 构建信息生成基线、Spring Boot build-info 配置基线 | 建议作为业务项目 parent |
| df-utility | R<T>、BusinessException、ErrorCode / CommonErrorCode、PageData、TraceContext、RequestContext、RequestContextHolder、ResponseSupport | 所有项目共享基础契约 |
| df-core-starter | 全局异常处理、统一响应自动包装、RequestContextFilter、@BusinessLog、JwtTokenService、OpenAPI/Swagger UI 文档能力、Actuator 健康检查与管理端点能力、Spring Boot 4 默认优雅停机基线 | Web 服务默认接入 |
| df-cloud-starter | @LoadBalanced RestClient.Builder、TraceId 请求头透传、灰度路由（`GrayTag` / `GrayScopes`）、配置中心接入 | 有服务间 HTTP 调用、需灰度调用或需接入 Nacos 时接入 |
| df-jpa-starter | BaseEntity（含 tenantId 只读字段）、BaseRepository、分页/投影原语、数据库平台工厂、方言自动配置、最大返回行数保护、**Hibernate StatementInspector 自动注入租户条件**（DML / SELECT / JOIN / 子查询 / CTE） | 使用 JPA 的服务必须接入 |
| df-dynamic-starter | @DS、动态数据源上下文、路由数据源基类 | 多数据源服务按需接入 |
| df-tenant-starter | 多租户能力聚合包（自动引入 df-jpa-starter 租户改写链路）；TenantProperties 配置位；TenantContext 兼容门面（已废弃，转发到 RequestContextHolder） | 需要显式声明“启用多租户”意图时接入；只用 JPA 时也可仅依赖 df-jpa-starter |
| df-redis-starter | RedisLockUtil、RedisUtil 自动装配 | 使用 Redis 锁或 Redis 常用操作时接入 |
| df-es-starter | IndexNameResolver、ES 基础属性 | 使用 ES 时接入 |
| df-message-starter | DfMessageTemplate、持久化发送账本、消费账本、运行时队列配置契约、补发告警骨架、Redis Stream/RabbitMQ 全局通道模式、RabbitMQ 队列治理属性 | 需要可靠消息发布、消费对账或消息兜底时接入；队列维护、发布下线和页面由业务基础服务承接 |
| df-test-starter | 基础测试支撑 | 测试模块按需接入 |

补充边界说明：

1. df-core-starter 当前提供的是轻量 JWT 服务，不等于完整认证授权框架。
2. 多租户上下文统一由 df-core-starter 的 RequestContextFilter 在请求入口从 `TenantId` 请求头写入 RequestContextHolder；缺失时使用默认租户 `0`。是否在网关/过滤器层强校验租户头由业务自行决定。
3. JPA 层的租户隔离由 df-jpa-starter 的 TenantSqlRewriter 在 Hibernate StatementInspector 阶段统一改写 SQL 完成（INSERT 注入列与值、UPDATE/DELETE/SELECT 注入 WHERE 条件，含 JOIN、子查询、CTE）。业务代码 **禁止** 自行 `setTenantId(...)` 或在 Specification / JPQL 中手写 `tenantId = ?`。当前框架内部若在 BaseEntity 中保留只读 `tenantId` 映射，也仅用于查询回填，不要求业务实体显式声明该字段。
4. df-tenant-starter 在新版本中作为“多租户能力聚合包”存在，本身不再注册 Web 拦截器；仅通过依赖 df-jpa-starter 来确保 SQL 改写链路就绪，并保留 TenantContext 作为兼容门面（@Deprecated，转发到 RequestContextHolder）。
5. df-dynamic-starter 当前只提供注解、上下文和路由数据源基类，真实数据源 Bean 仍需业务项目自行装配。
6. df-es-starter 是轻量封装。
7. df-message-starter 已开始落地持久化消息链路，数据库消息表是事实来源，Redis Stream/RabbitMQ 是传输通道；当前仍不是完整消息中台，不内置管理端 UI、队列发布下线工作流或第三方告警 SDK。
8. df-core-starter 已内置 Spring Boot Actuator；默认仅暴露 `/actuator/health`，如需网关聚合版本信息，业务服务必须在 Nacos 或本地配置中显式暴露 `health,info`。
9. Spring Boot 4 已默认启用 Web 容器优雅停机，业务服务不再迁移或新增旧版 `GracefulShutdownConfig`、`TomcatConnectorCustomizer` 等手工停机实现；只需按需调整 `spring.lifecycle.timeout-per-shutdown-phase`。

### 4.4 推荐最小依赖组合

| 场景 | 推荐最小依赖 |
|------|--------------|
| 纯 Web API 服务 | df-core-starter |
| Web + JPA 服务 | df-core-starter + df-jpa-starter |
| Web + JPA + 多租户 | df-core-starter + df-jpa-starter + df-tenant-starter |
| Web + Redis 锁 | df-core-starter + df-redis-starter |
| Web + 消息发布/消费对账 | df-core-starter + df-jpa-starter + df-message-starter |
| 需要调用其他微服务 | 在上述组合基础上增加 df-cloud-starter |

最常见的 Web + JPA + 多租户服务接入方式：

```xml
<dependencies>
    <dependency>
        <groupId>com.df</groupId>
        <artifactId>df-core-starter</artifactId>
    </dependency>
    <dependency>
        <groupId>com.df</groupId>
        <artifactId>df-jpa-starter</artifactId>
    </dependency>
    <dependency>
        <groupId>com.df</groupId>
        <artifactId>df-cloud-starter</artifactId>
    </dependency>
    <dependency>
        <groupId>com.df</groupId>
        <artifactId>df-tenant-starter</artifactId>
    </dependency>
</dependencies>
```

接入要求：

1. 按场景选最小组合接入，不要无差别引入全部 starter。
2. 除 df-utility 外，业务项目通常不应直接依赖非 starter 的基础模块实现。

## 5. 项目级配置中心基线

### 5.1 总体原则

本项目统一采用 Nacos 分层配置方案。所有中间件连接地址、密码、密钥都是环境相关敏感信息，不应硬编码进代码仓库。

分层原则如下：

1. 本地 application.yml 只保留 Nacos 连接信息和配置导入入口。
2. 公共基础设施配置统一放入 df-shared-infra.yaml。
3. 服务专属配置统一放入 服务名.yaml。
4. 数据库连接、JPA 参数、服务端口、租户开关、JWT 密钥等运行配置不再保留在本地 application.yml 中。
5. 示例工程中用于演示的 application-local.yml、本地 datasource 等内容，仅用于说明接入方式，不作为当前医共体服务的正式基线。

### 5.2 application.yml 允许保留的内容

当前正式基线下，本地 application.yml 只允许保留：

1. spring.application.name
2. spring.cloud.nacos.server-addr
3. spring.cloud.nacos.config.namespace
4. spring.cloud.nacos.config.group
5. spring.config.import

除此之外，数据库连接、JPA 参数、服务端口、租户开关、JWT 配置、消息与缓存连接信息，都必须进入 Nacos 分层配置。

推荐写法：

```yaml
spring:
  application:
    name: df-ygt-biz-huanzhe360
  cloud:
    nacos:
      server-addr: ${NACOS_ADDR:127.0.0.1:8848}
      config:
        namespace: ${NACOS_NAMESPACE:}
        group: ${NACOS_GROUP:DEFAULT_GROUP}
        file-extension: yml
  config:
    import:
      - nacos:df-shared-infra.yaml
      - nacos:${spring.application.name}.yaml
```

### 5.3 Nacos 分层方案

| 层级 | 存放位置 | 内容 | 适用范围 |
|------|----------|------|----------|
| 本地引导层 | application.yml | 服务名、Nacos 地址、命名空间、分组、配置导入入口 | 所有环境 |
| 共享基础设施层 | Nacos 的 df-shared-infra.yaml | Redis、RabbitMQ、ES、通用中间件连接与共享配置 | 跨服务共享 |
| 服务专属层 | Nacos 的 服务名.yaml | DataSource、JPA、JWT、服务特有参数、端口、租户开关等 | 单个服务 |

共享配置建议内容：

1. spring.data.redis.*
2. spring.rabbitmq.*
3. spring.elasticsearch.*

服务专属配置建议内容：

1. spring.datasource.*
2. spring.jpa.*
3. df.security.jwt.*
4. df.jpa.max-row-limit.*
5. df.message.rabbit.management.*
6. tenant.*
7. server.port
8. management.endpoints.web.exposure.*
9. spring.lifecycle.timeout-per-shutdown-phase

### 5.4 Nacos 本地覆盖规则

本地联调若需覆盖 Nacos 地址，仅允许通过以下环境变量调整：

1. NACOS_ADDR
2. NACOS_NAMESPACE
3. NACOS_GROUP

不得在 application.yml 中回填数据库地址、Redis 地址、RabbitMQ 地址等运行配置。

### 5.5 敏感信息要求

1. 敏感配置不允许硬编码进仓库。
2. 连接信息放入 Nacos 只是第一步，生产环境强烈建议启用配置加密或对接密钥系统。
3. 生产环境的 JWT secret 必须替换默认值，不允许继续使用示例密钥。

### 5.6 日志配置基线

1. 业务服务如需在 Logback 配置中读取 `spring.application.name` 等 Spring Environment 属性，日志配置文件名必须使用 `logback-spring.xml`，不要继续使用普通 `logback.xml`。
2. 服务日志名统一跟随 `spring.application.name`，推荐通过 `springProperty` 映射为 `APP_NAME` 后复用，避免在日志文件名、上下文名里重复手写服务名。
3. 示例工程和通用模板中的日志目录统一使用 `logs` 作为默认目录，并允许通过 `logs.dir` 外部覆盖；日志文件命名统一采用 `${APP_NAME}.log`、`${APP_NAME}-error.log`。
4. 常规服务日志至少保留三类输出：控制台日志、应用主日志、错误日志。主日志与错误日志统一采用按天加按大小滚动，避免单文件无限增长。
5. 当前接入基线不再依赖 SkyWalking 专用 Logback Layout。通用脚手架、示例工程、可分发模板中禁止直接依赖 `org.apache.skywalking` 日志类。
6. `df-core-starter` 会在 `RequestContextFilter` 中自动写入 `traceId`、`requestId`、`tenantId` 等 MDC 字段；日志 pattern 可直接通过 `%X{traceId}`、`%X{requestId}` 输出链路标识，不要为了输出链路标识额外引入 APM 厂商专用日志实现。
7. `spring.application.name` 仍属于 application.yml 引导层允许保留的内容，因此服务改名后，日志上下文名与日志文件名应自动跟随，不需要再单独修改 Logback 配置中的硬编码服务名。
8. `df-core-starter` 已内置统一 HTTP 请求/响应日志埋点：总开关 `df.core.web.logging.enabled` 默认开启，请求入口和响应出口默认记录 URL、headers、query、客户端地址、状态码和执行时间，替代历史 `HttpTraceRepository` 方案。
9. 接口 body 日志不是默认全开，而是通过 `df.core.web.logging.body-path-patterns` 按路径单独开启；这样默认观测链路完整，但只有命中的少量接口才承担 body 复制与序列化成本。
10. `df.core.web.logging.body-path-patterns`、`df.core.web.logging.max-body-length`、`df.core.web.logging.masked-header-names` 这类行为配置应优先进入服务专属 Nacos 配置；配置中心新增某个接口路径后，后续新请求应立即生效，删除后也应立即停止打印，无需重启服务。
11. 默认会记录全部请求头，但 `Authorization`、`Cookie`、`Set-Cookie` 等敏感头必须按名称脱敏；body 日志仅用于临时观测与排障，命中接口时仍须遵守脱敏要求，身份证号、手机号、token、密码、密钥等敏感字段不得全量输出到日志。
12. 可直接放入服务专属 Nacos 的日志配置样例见 10.3 节；新服务不要只在 README 或示例工程里找片段，接入时以本节模板为准。

## 6. 启动与包结构基线

### 6.1 启动类要求

1. 启动类必须位于业务项目根包。
2. 必须保证组件扫描覆盖业务代码与 starter 自动装配后的 Bean 使用场景。

推荐结构：

```text
com.xxx.yourservice
├── controller
├── service
├── repository
├── model
└── YourServiceApplication
```

### 6.2 组织域目录要求

机构、组织、科室、人员等同属组织域的模块，代码目录统一归入 domain/org 父域，不再平铺散落多个同级包。

## 7. 本项目租户与认证边界

### 7.1 多租户策略

本项目当前租户策略如下：

1. 一期默认支持多租户，但暂不启用租户隔离。
2. 所有核心业务表必须保留 tenantid 字段，且 DDL 默认值固定为字符 `0`。
3. 接口契约与跨服务调用契约保留 TenantId。
4. 业务开发阶段不允许显式 `getTenantId()` / `setTenantId(...)` 操作实体租户字段；租户读写统一由请求上下文与 SQL 改写链路托管。
5. 不再接受“tenantid 字段允许为空”的旧规则；新表、改表、初始化 DDL 必须落成 `not null default '0'`。
6. 后续启用多租户时，不允许再做破坏式改表。

标准建表模板与字段级约束，统一以 [03-业务开发与接口实现规范.md](03-业务开发与接口实现规范.md) 中“关于租户字段，统一处理如下”后的 DDL 模板为准。

### 7.2 认证职责边界

1. 本项目不负责账号密码登录。
2. 本项目负责用户主体映射、角色权限治理、认证配置管理。
3. 若业务服务要求登录态校验，需要在业务项目中补自己的认证入口。
4. Token 的生成与解析统一复用 JwtTokenService，不允许自造第二套 token 服务。

## 8. API 文档接入基线

### 8.1 文档能力来源

1. 接入 df-core-starter 后，默认获得 springdoc-openapi 文档能力。
2. 不再额外引入 Swagger 或 Knife4j starter。
3. 默认在线文档入口包括：
   1. /v3/api-docs
   2. /v3/api-docs.yaml
   3. /swagger-ui/index.html

### 8.2 运行时行为说明

当前脚手架已做以下统一处理：

1. OpenAPI 端点不会再被统一响应包装成 R<T>，避免 Swagger UI 读取文档失败。
2. 业务接口的 OpenAPI 响应模型会自动对齐为 R<T> 外层结构，而不是只展示裸 DTO。
3. 所有接口会基于 RequestContextHolder 中定义的请求头常量，自动补齐全局 Header 参数说明。

### 8.3 配置边界

1. df.core.api-doc.* 用于配置标题、描述、版本、联系人、许可证和默认 JWT Bearer 安全方案。
2. springdoc.* 继续保留原生配置能力，可控制扫描包、分组、UI 路径、是否暴露 UI 等。

### 8.4 生产环境暴露建议

1. 若生产环境不需要交互式页面，可设置 springdoc.swagger-ui.enabled=false。
2. 若连 OpenAPI 端点也不希望暴露，可进一步设置 springdoc.api-docs.enabled=false。

## 9. 关键配置项附录

### 9.1 Actuator 管理端点配置

接入 `df-core-starter` 后，业务服务默认具备 Spring Boot Actuator 能力。Spring Boot 4.0.5 默认 Web 暴露范围仅包含 `health`，因此默认可访问：

1. `/actuator/health`

默认不暴露 `/actuator/info`、`/actuator/metrics`、`/actuator/env` 等端点。若网关、前端或监控平台需要聚合服务版本信息，服务专属 Nacos 配置中应显式声明：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info
```

生产环境不得直接配置 `management.endpoints.web.exposure.include=*`，除非已有独立管理端口、访问控制和安全审计方案；`env`、`configprops`、`beans` 等端点默认不应对业务网络开放。

### 9.9 优雅停机配置

Spring Boot 4.0.5 对内嵌 Tomcat、Jetty、Reactor Netty 的 Web 应用默认启用 graceful shutdown。应用收到正常关闭信号并开始关闭 Spring ApplicationContext 时，Web 容器会停止接收新请求，并允许已经进入处理流程的请求在超时时间内完成。

因此，业务服务不需要再实现旧版 demo 中的 `GracefulShutdownConfig`，也不需要手工定制 Tomcat Connector、暂停端口或轮询线程池。该能力属于 Spring Boot 4 基线能力，重复实现会带来停机顺序不一致、容器升级不兼容和线程池等待逻辑漂移。

当前只建议按服务特性调整停机等待时间：

```yaml
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

配置边界如下：

1. 不配置时使用 Spring Boot 默认值 `30s`。
2. 长接口、批处理回调或外部系统同步较多的服务，可在服务专属 Nacos 配置中按需调大，例如 `60s`。
3. 不要配置 `server.shutdown=immediate`，除非明确要求关闭优雅停机。
4. IDE 停止按钮、`kill -9`、容器强杀等不会完整触发优雅停机；生产环境应由部署平台发送正常终止信号，并保证平台的 termination grace period 大于或等于本配置。
5. HTTP 优雅停机只处理 Web 容器请求收尾；RabbitMQ 消费、定时任务、异步线程池、长事务等后台任务仍需按各自组件生命周期单独治理。

### 10.3 服务专属 Nacos 配置模板

```yaml
server:
  port: 8080

management:
  endpoints:
    web:
      exposure:
        include: health,info

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
  datasource:
    url: jdbc:mysql://127.0.0.1:3306/demo
    username: root
    password: 123456
    driver-class-name: com.mysql.cj.jdbc.Driver
  jpa:
    hibernate:
      ddl-auto: validate

tenant:
  enabled: true
  isolation: field

df:
  core:
    web:
      logging:
        enabled: true
        # 请求/响应 body 最多记录前 4096 个字符；超过部分会截断
        max-body-length: 4096
        # 这些请求头仍会记录键名，但值会被替换为 ***，避免 token/cookie 泄露
        masked-header-names:
          - Authorization
          - Cookie
          - Set-Cookie
        # 只有命中这些路径时才额外打印 body；URL、headers、query、状态码、耗时仍默认打印
        body-path-patterns:
          - /api/base/patients
          - /api/base/patients/**
  security:
    jwt:
      issuer: df-platform
      secret: change-me-before-production-change-me-before-production
      expiration: 2h
  jpa:
    database-type: mysql
    auto-configure-hibernate-dialect: true
    max-row-limit:
      enabled: true
      max: 2000
      level: error
```

## 11. 接入验收清单

新服务接入完成后，至少自查以下事项：

1. 是否已继承 df-parent 或导入同版本 BOM。
2. 是否只引入必要 starter，而不是全部引入。
3. 是否没有在子模块自行钉第三方依赖版本。
4. 是否已按项目基线改为 Nacos 分层配置。
5. application.yml 是否只保留 Nacos 连接与配置导入入口。
6. 是否已将公共配置放入 df-shared-infra.yaml，将服务专属配置放入 服务名.yaml。
7. 是否已替换生产环境 JWT secret。
8. 是否已明确本项目当前租户策略与认证边界。
9. 启动类是否位于根包，扫描范围是否正确。
10. 是否明确新服务所需 starter 组合与可选能力边界。
11. 是否未将敏感配置硬编码进仓库。
12. 是否同步理解并准备遵守 02、03、04 三篇规范。
13. 是否至少跑通一条成功链路。
14. 是否至少跑通一条参数校验失败链路。
15. 是否至少跑通一条业务异常链路。
16. 是否确认 `/actuator/health` 可用；如依赖版本聚合，是否已显式暴露 `/actuator/info`。
17. 是否没有新增旧式 `GracefulShutdownConfig` 或手工 Tomcat Connector 停机逻辑；如需调整停机等待时间，是否仅通过 `spring.lifecycle.timeout-per-shutdown-phase` 配置完成。

## 12. 最终原则

接入脚手架，意味着接受统一底座约束，而不是把 starter 当普通 jar 使用。凡是版本、接入、配置、租户、认证边界与本文档冲突的实现，都视为接入未完成。
