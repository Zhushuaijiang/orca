# AI协作与代码评审规范

## 1. 文档定位

本文档用于约束 AI 辅助开发输出、代码评审行为和规范治理方式，目标是：

1. 防止 AI 在业务服务中重复设计脚手架基础能力。
2. 让 PR 评审、联调验收、规范维护有统一口径。
3. 保证 README 的准入门禁与实际开发、评审流程形成闭环。

## 2. AI 协作硬规则

向 Copilot、Agent 或其他 AI 下达开发任务时，应默认附带以下约束：

1. 只允许在现有脚手架职责边界内补业务代码，不允许自创基础设施层。
2. 发现仓库已有同类基础能力时，必须优先复用，不允许平行造轮子。
3. 涉及 DTO 状态跟踪时，优先基于 DTOBase。
4. 涉及分布式唯一 ID 时，优先基于 SequenceUtil 或脚手架统一封装。
5. 涉及统一响应、异常、错误码、TraceId、租户上下文、Redis 锁、消息发布、JPA 基类时，必须使用脚手架现有实现。
6. 若脚手架能力不足，优先提出“扩展脚手架”的建议，而不是在服务内复制实现。
7. 任何新增或调整脚手架能力、starter 依赖、自动配置、默认暴露端点、响应包装例外或配置默认值的变更，都必须同步更新 `docs/output` 与必要的 README 说明。
8. 生成代码前，必须先阅读 README，并按顺序学习 01、02、03 三篇规范。

## 3. AI 禁止输出的内容

AI 生成结果中，禁止出现以下类型产物：

1. 新的 BaseDTO、DTOBase、EntityStateTracker 一类的 DTO 基类。
2. 新的 SequenceUtil、SnowflakeIdWorker、IdGenerator 一类的 ID 生成器。
3. 新的统一响应壳、统一异常壳、统一错误码枚举。
4. 在业务模块创建与脚手架已有职责重复的 comm、base、context、support 公共层。
5. 在子模块随意声明第三方依赖版本。
6. 把脚手架级问题下沉到业务服务自己解决。
7. 把示例工程写法直接扩展成与主规范冲突的另一套强制规范。

## 4. 建议的 AI 提示词模板

可在生成代码前附加以下约束：

```text
基于 df-java-base 脚手架补业务代码。
只允许复用现有脚手架能力，不允许新增第二套基础设施实现。
涉及 DTO 状态跟踪时必须优先复用 DTOBase。
涉及分布式 ID 时必须优先复用 SequenceUtil。
禁止生成新的统一响应体、统一异常、统一错误码、Snowflake、BaseDTO、通用上下文工具类。
如发现脚手架能力不足，优先提出扩展脚手架方案，而不是在业务模块旁路实现。
如果修改脚手架能力、starter 依赖、自动配置、默认端点、响应包装例外或配置默认值，必须同步更新 docs/output 与必要的 README；文档未同步视为任务未完成。
生成任何代码前，先阅读 README，并按顺序学习 01-接入基线与配置规范、02-基础能力复用与架构红线、03-业务开发与接口实现规范。
```

## 4.1 可直接复制到 AI 规则文件的摘要

如需给 Copilot、Agent、Cursor 或其他代码生成工具配置项目级规则，优先使用以下摘要：

```text
本项目基于 df-java-base 脚手架开发，生成代码时必须遵守以下规则：

1. Controller 对外返回统一遵循 R<T> 协议，不新增第二套 Result/Response 壳。
2. 业务异常统一使用 BusinessException。
3. 公共错误码优先使用 CommonErrorCode，并遵守既有码段语义。
4. JPA 实体默认继承 BaseEntity。
5. Repository 默认继承 BaseRepository。
6. HTTP Trace 头统一使用 TraceId。
7. 租户头统一使用 TenantId。
8. DTO 状态跟踪统一复用 DTOBase。
9. 分布式 ID 统一复用 SequenceUtil。
10. 常规 DTO 与实体转换优先使用 ConverterUtil。
11. 分布式锁统一使用 RedisLockUtil。
12. JWT 统一使用 JwtTokenService。
13. 消息发布统一使用 MessagePublishTemplate；routeKey 监听统一优先使用 @DfMessageRouteKeyListener。
14. 不得重复实现脚手架已提供的基础能力。
15. 修改脚手架能力、starter 依赖、自动配置、默认端点、响应包装例外或配置默认值时，必须同步更新 docs/output 与必要的 README。
16. 生成任何代码前，必须先阅读 README 和 01-04 四篇规范。
```

## 5. 代码评审关注点

评审 AI 产物或人工代码时，优先检查以下问题：

1. 是否重复实现了脚手架已有基础类。
2. 是否把脚手架级问题下沉到业务服务自己解决。
3. 是否引入了子模块级第三方版本或绕开 parent 管理。
4. 是否把规划写成现状，或把示例写成强制规范。
5. 是否同步更新了相应文档；涉及架构能力、starter、自动配置、默认端点、响应包装例外或配置默认值的变更，文档未同步即视为未完成。
6. 是否遵守了 README 的开发准入门禁和强制阅读顺序。

## 6. PR 必查项

PR 提交前，必须确认以下事项：

1. 提交人是否已完整阅读 README 与 01-04 四篇规范。
2. 是否复用了脚手架已有基类和工具，而不是新建重复实现。
3. 是否没有在子模块新增第三方依赖版本。
4. 是否没有把 target、日志、生成物、临时调试文件提交进仓库。
5. 是否同步更新了相关 README、架构说明或规范文档；凡是脚手架能力、starter 依赖、自动配置、默认端点、响应包装例外或配置默认值发生变化，必须有对应文档差异。
6. 是否明确区分了“当前已实现”和“后续规划”。
7. 是否没有把示例工程或历史遗留写法误写成当前主规范。

## 7. 通过标准与验收口径

只有同时满足以下条件，产物才可进入主干：

1. 没有新增脚手架重复能力。
2. 与 df-parent、各 starter、df-utility 的职责边界一致。
3. 输出文档、配置方式、代码实现口径一致。
4. 评审人员可以明确指出“复用了哪一项既有脚手架能力”。
5. 已完成 README 要求的开发准入学习，不存在未读规范直接开工的情况。

满足以下条件，才能判定服务开发符合脚手架规范：

1. 依赖、包结构、基础协议与基础设施复用方式符合脚手架统一约束。
2. 没有出现重复发明 DTOBase、SequenceUtil、统一响应、统一异常等基础能力。
3. 接口、异常、配置、日志、租户、Trace、消息、数据访问入口均遵循已有基线，且接口 API 声明完整可用。
4. 文档与代码口径一致，没有“代码这样做、文档却写成另一套规范”的情况。

### 7.1 最小运行验收动作

以下动作属于联调前最低运行验收要求，不得只做静态自查：

1. 至少跑通一条成功链路。
2. 至少跑通一条参数校验失败链路。
3. 至少跑通一条业务异常链路。

若上述三类链路没有实际验证，视为验收不完整。

## 8. 文档治理规则

### 8.1 已实现与规划中的口径治理

1. 文档只描述当前已确认且允许下游使用的能力，不把规划写成现状。
2. 不得把规划能力、候选方案、示例写法写成当前强制规范。
3. 不得出现“代码已变更但文档仍描述旧结构、旧版本、旧接口”的不对称状态。

### 8.2 规范同步要求

1. 每次沟通新增的开发规格，必须按主题分类同步到对应主文档。
2. 若代码实现已调整但规范文件未同步，视为任务未完成。
3. README 必须同步维护阅读顺序、准入门禁和单点权威主题索引。
4. 不允许再把同一主题分散复制到多篇文档正文中形成双轨描述。
5. 脚手架能力、starter 依赖、自动配置、默认端点、响应包装例外、配置默认值、对外接入方式发生变化时，必须在同一任务中同步更新 `docs/output` 对应文档；否则不进入发布或交付。

### 8.3 主文档分工

1. 01 负责接入基线、版本与配置。
2. 02 负责基础能力、上下文与基础设施复用红线。
3. 03 负责实体、DTO、接口与 OpenAPI 实现规范。
4. 04 负责 AI 协作、评审、治理与验收口径。

## 9. 最终原则

AI 协作和代码评审的目标，不是“尽快生成代码”，而是确保业务代码始终落在既有脚手架边界内，且规范、配置、实现、评审口径保持一致。凡是未先学习开发指南就直接开工的行为，都视为流程不合格。
