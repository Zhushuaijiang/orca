# DFHIS 前端单元测试规范

> 配套技能包：`dfhis-frontend-unit-test-guide`（精简门禁 + 落地流程）。本文为完整规范。
>
> 默认基线：Vue 2 + Vue CLI 4 + `@vue/cli-plugin-unit-jest` 4.5.x + Jest。Vue 3 + Vite + Vitest 仓库按本仓实际配置套用同样原则。
>
> 项目特定内容（路径别名、运行器版本、本仓案例）请参考各 `df-web-*` 仓的 `tests/README.md` 与 `tests/unit/README.md`。

## 1. 项目是否值得做单元测试

DFHIS 前端（df-web-zhuyuanysz、df-web-menzhenysz、df-web-bingangl、df-web-cdr、df-web-pishisy 等）适合"**选择性补充单元测试**"：

- 优先为高风险、可独立验证的业务规则补充测试，收益较高。
- 不为覆盖率给所有历史 Vue 页面补测试——维护成本远超收益。
- 页面展示、组件交互、DevExtreme 集成、完整业务流程仍以人工验证或端到端测试为主。

直接挂载完整页面通常需要大量 Mock（Vuex 状态、DevExtreme 全局组件、mixin、路由、患者/科室/参数上下文），测试编写和维护成本极高。**因此，优先将复杂判断或计算逻辑抽成纯函数，再对纯函数编写单元测试。**

## 2. 推荐测试范围

优先补充单元测试的代码：

- 医嘱状态转换、频次和领药方式判断。
- 剂量、用量、金额、天数、取整与舍入计算。
- 处方拆分、合并、分组规则。
- 参数、权限、状态组合判断。
- 接口数据转换、字段归一化、提交数据组装。
- 表单校验规则、错误码映射。
- 可编辑复制、批量处理、合并视图的差异计算。
- 出现过线上问题、测试打回、容易破坏旧行为的代码。

不优先写单元测试：

- 只有简单赋值的代码。
- 表格列、静态文案、样式配置。
- 主要依赖 DevExtreme 或全局组件交互的页面代码。
- 没有业务判断的普通增删改查。
- 框架自身已经保证的行为。

## 3. 目录与命名

- 测试目录：`tests/unit/`（仓库根级别）。
- 包路径与生产代码一致：使用 `@/...` 别名（与生产代码 `import` 完全一致）。
- 文件名：被测模块名 + `.spec.js`，例：`editableCopyLingYaoFs.spec.js`。
- `describe` 标题：被测业务能力（例 `describe('DFHIS-31989 可编辑复制医嘱的领药方式处理', ...)`），DFHIS 需求必带需求编号便于追溯。
- `test` 标题：业务行为 + 预期（例 `test('频次未改变时保留临时领药及用量', ...)`），避免"测试一""测试正常"等无意义命名。

## 4. 编写规则

1. **先抽纯函数**再写测试：把业务判断抽到 `src/<module>/utils/xxx.js`，测试只导入纯函数。
2. **Arrange/Act/Assert** 三段组织测试。
3. **覆盖真实风险**：
   - 正常路径。
   - 不满足条件时的旧行为（保护回归）。
   - 临界值、空值、异常值。
   - 后端可能返回的数字、字符串等不同数据类型。
   - 是否意外修改了与当前规则无关的字段。
4. **断言完整业务结果**，不只断言 `toBeDefined` 或 `toBeTruthy`。
5. **测试直接调用生产代码**，不能复制一份实现做"白盒镜像"。
6. **不修改生产代码以适应测试**——若生产代码难测，优先抽函数而非放宽 `public`。
7. **不依赖时间/随机数/环境/执行顺序**；固定 `now`、mock 时钟。
8. **不依赖外部资源**（接口、数据库、Redis、Nacos、文件、第三方服务）—— 全部 mock。

## 5. Jest 规则

- 只 mock 外部协作者：接口（axios/fetch）、消息发送器、时钟、文件客户端、Vuex/getter。
- 不 mock 被测模块本身。
- 只定义当前用例需要的 stub；用完在 `@afterEach` 清理（`jest.clearAllMocks`）。
- 副作用用 `expect(mock).toHaveBeenCalledWith(...)` 验证参数与次数。
- 复杂参数使用 `toHaveBeenCalledWith` + 精确值；少用 `expect.any()` 模糊匹配。
- 异步用 `await` + 真实 Promise，不用 `setTimeout` 等真实时间。
- 文件首行必须 `/* eslint-env jest */`，避免 ESLint 误报未使用变量。

最小可运行示例：

```js
/* eslint-env jest */
import { getEditableCopyLingYaoFsPatch } from '@/pages/bingRenTabs/yiZhuKaiLi/utils/editableCopyLingYaoFs'

describe('DFHIS-31989 可编辑复制医嘱的领药方式处理', () => {
  test('改为不同的长期频次时只清空领药方式', () => {
    // Arrange
    const source = { pinCi: 'ONCE', changQiLsBz: 2, lingYaoFsId: 8 }
    const row = { pinCi: 'BID', pinCiLx: 1 }

    // Act
    const result = getEditableCopyLingYaoFsPatch(row, source)

    // Assert
    expect(result).toEqual({ lingYaoFsId: null, lingYaoFsMc: null })
  })
})
```

## 6. 分层边界

- **Utils 纯函数**：单测核心层，零依赖，最优先测。
- **Vuex store getters/actions**：可单测；mock 内部 mutation/action 后调用 getter。
- **单文件组件 (`*.vue`)**：高价值集成测试才挂载（`@vue/test-utils` `mount`），且必须 mock 全部 mixin、全局组件、`$route`/`$store`。
- **多组件组合**：jest 只能跑单个组件；多组件交互用 Cypress/Playwright 端到端。
- **HTTP 集成**：用 MSW (Mock Service Worker) mock 后端响应；不要真打后端。

## 7. 执行

默认基线 Vue CLI 4 + Jest：

```powershell
# 全部 unit
yarn test:unit

# 单个 spec
yarn test:unit tests/unit/<name>.spec.js

# 按名称匹配
yarn test:unit -t "频次未改变"

# 串行（CI 稳定）
yarn test:unit --runInBand

# 覆盖率
yarn test:unit --coverage
```

开发时单文件跑通；提交前跑模块全量；失败时定位首个根因，不靠重复运行掩盖不稳定。

## 8. 提交检查

- [ ] 复杂判断/计算已抽成 `src/.../utils/xxx.js` 纯函数
- [ ] 文件名 `被测模块名.spec.js`，目录 `tests/unit/`
- [ ] 覆盖真实风险：正常、边界、不满足条件时的旧行为、临界/空/异常值
- [ ] 不挂载 Vue、不依赖 Vuex/DevExtreme/全局组件/接口/患者上下文
- [ ] Mock 仅用于外部协作者（接口、时钟、文件、消息）
- [ ] 断言有业务意义，测试直接调用生产代码
- [ ] 测试独立、可重复，已运行相关测试和模块全量测试
- [ ] 不为覆盖率堆砌断言；断言检验业务结果（`toEqual`/`toBe` 完整值）
- [ ] 若属 DFHIS Reopen 修复，引用 DFHIS 编号在 describe 标题

## 9. 单元测试的能力边界

单元测试可以验证独立业务函数的规则是否正确，但不能单独保证：

- 页面一定调用了该函数（必须靠 code review 或端到端）。
- 下拉框/表格事件一定触发（必须靠端到端）。
- 接口返回的数据一定符合约定（必须靠契约测试）。
- 页面展示和样式一定正确（必须靠人工截图）。
- 完整医嘱保存链路一定成功（必须靠端到端）。

推荐的测试结构是：

```text
大量高价值的业务单元测试（utils 纯函数）
少量关键模块的集成测试（store / 关键组件）
少量核心业务链路的端到端测试（Cypress / Playwright）
```

## 10. 落地策略

1. 新增复杂业务规则时，同步抽取纯函数并补充测试。
2. 修复线上问题或测试打回时，至少补充一个可复现问题的回归用例。
3. 计算类逻辑覆盖正常值、边界值和异常值。
4. 页面展示和 DevExtreme 交互继续以人工验证为主。
5. 暂时不要求全项目达到固定覆盖率。
6. 提交代码前执行 `yarn test:unit`，确保已有业务规则没有回归。

这套测试体系的定位是**保护高风险业务规则**，而不是为项目中的每一个 Vue 页面补齐单元测试。
