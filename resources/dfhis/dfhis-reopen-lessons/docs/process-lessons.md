# 通用流程教训

来源：DFHIS-31833 被重打开 3 次及后续多次复盘，根因都是流程性/口径性失误而非技术难题。新增流程教训追加在本文件末尾，SKILL.md 索引只加一行。

## 1. SQL 附件必须与最终交付一致

测试反馈"两个附件 SQL 都不是最新的"。SQL 有任何改动，必须重新上传附件，评论中写明附件 id 和字节数，并保证 `数据变更` 字段、附件、仓库内 SQL 文件三者一致。

## 2. 测试反馈逐条闭环

一次反馈常含多个编号问题。修复评论必须按原编号逐条对应答复；未修的说明原因和计划，不允许只修一部分就交付。

## 3. "待发布后验证"要主动跟踪

首次交付遗留的发布后验证项若无人跟进，就会以重打开的形式回来。交付评论中列出待发布后验证清单，发布后主动验证关闭，不等测试发现。

## 4. 重打开交付后的负责人/参与人必须服从本需求的显式流转口径

默认可将负责人改回最新测试反馈/重打开评论作者并保留相关参与者，但用户明确要求"转给合适开发"或"参与人只要 1 人"时，不得沿用默认规则。应重新按代码归属选择开发者，将 `assignedTo` 和唯一参与人设为同一人，并在字段回写后读回人数与 userId。DFHIS-31915 第 4 轮交付因此保持前端开发杨国栋为负责人和唯一参与人，而不是转给重打开评论作者。

## 5. 增量推送默认保留已确认负责人，不得把字段回写脚本的自动选人规则当成改派授权

DFHIS-31967 revision 16 已处于开发测试且负责人/唯一参与人为陆继勇，agent 在仅追加两个前端提交时擅自改派杨国栋，随后被用户要求恢复。正确做法是先区分"首次流转/用户要求改派"和"同一需求增量提交"：后者若用户未要求改负责人，应保留当前 `assignedTo/participants`，只追加变更字段与评论；若所用脚本强制要求 `--assignee`，显式传当前已确认负责人并在写后回读。只有用户明确要求重新分配时，才执行技术偏向选人。

## 6. 跨会话/跨天恢复在途需求前先重拉云效最新评论，不要复用上次归档的评论快照

DFHIS-31879 于 08-04 已 push V1（门诊轮询 + 住院 jj/lc 端点），08-13 继续时 agent 直接复用旧本地归档（`yunxiao-requirement-archiver` HIS Code-Fix 第 1 步 "reuse the existing local archive" 措辞强化了这个倾向），未发现这 9 天客户已在云效评论里把刷新方案从轮询改为消息推送、把第三方回写入口统一到 mic-sapi，导致 V1 三个端点全部作废、需 revert RC，最终靠用户提示"需求发生变动，看最新的云效评论"才发现。任何在途需求跨会话/跨天恢复（尤其带活跃评论线程的三方对接类）前，必须先重跑 `run_direct_archive.py` 或至少 `list_work_item_comments` 拉最新评论，把"上次归档的评论"视为可能过期，确认需求未变再继续实现或 push，不要等用户提示。

## 7. 费用/金额类生产 bug 必须先 diff 好/坏版本锁定回归提交，禁止只按表象加兜底

洛宁重复计费（2026-8-11 爆发）第一轮 agent 没先定位回归源，按"有重复行"的表象在保存收口加 `uniqYiZhuFyForSave` 去重兜底并推了 5 条分支，结果只挡住同项目复活，没挡住真正的回归路径（`297bed05` 旧费用无条件标 Delete 回塞 → 保存前 New 分支强制矫正复活 → xiangMuLx>=10 绕过去重；换项目残留型新旧 xiangMuId 不同，任何去重都挡不住），被迫返工第二刀。正确顺序：先拿到好/坏版本号做 `git log/diff` 锁定唯一费用生命周期改动 → 针对回归机制修复 → 再按 `dfhis-yizhu-kaili` 的强制校验场景矩阵逐场景断言"有效费用行数 == 预期"。表象兜底只能作为最后一层，不能作为修复本身。

## 8. HIS 改动必须同步单元测试，零测试交付一律不合格

用户明确要求（2026-08-14）：修改 HIS 相关需求时若缺少相应单元测试，后续 AI 扫描会判定为不合格修改。因此改完一个云效需求后必须及时添加单元测试，巩固每个模块的质量防护网。执行口径：单元测试与代码改动同一次 push 交付，覆盖本次主场景 + 每个被触碰分支的回归保留，遵循仓库既有测试约定（df-web 前端用 `tests/<功能目录>/xxx.test.js` 纯 node + assert，后端沿用既有 JUnit 测试树）；仓库没有测试设施不是豁免理由，按最轻量既有约定补建；交付评论写明测试文件路径、场景数和运行结果，`build/lint 通过` 不能替代。权威流程见 `his-workflow-harness` 的 Unit Test Gate 与 `yunxiao-requirement-archiver` HIS Code-Fix Workflow 第 10 步；医嘱开立模块另有更严的场景矩阵要求（`dfhis-yizhu-kaili`），叠加适用。
