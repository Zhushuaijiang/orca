# HIS 业务口径教训

每条含真实需求号、根因、错误做法、正确做法。新增业务教训追加在本文件末尾，SKILL.md 索引只加一行。

## 共享组件 opt-in 必须隔离返回值、控制流与副作用

- DFHIS-31998 的首次交付给共享诊间结算方法增加 `structuredOutcome` 参数，只隔离了返回结构；正常空、过滤后空、catch、错误提示、事件和提前返回等新增副作用仍对未 opt-in 的收费前台生效。错误做法是把“旧调用方仍拿到 `undefined`”当成完整向后兼容；返回值相同并不代表预结算调用次数、内部状态、事件、提示或控制流相同。
- 共享组件新增错误语义、结构化状态或失败传播时，应使用默认关闭的**组件级 opt-in**，目标页面显式开启；方法级参数只控制返回形态，且必须与组件 opt-in 同时满足。未开启路径要逐分支对照原基线，至少覆盖 provider falsy、对象空数组（有/无指定 ID）、过滤后空、catch、取消、业务失败（有/无错误文案）、成功和优惠重算空结果，并断言返回值、事件、提示、旧状态保留及下游调用次数。
- 目标页面的 opt-in 不能只靠人工看模板；增加契约测试证明最终模板确实传入 Boolean prop。保存/刷新失败状态还要测试提示次数、loading 复位、Promise 单次收口和停止对应下游。任何 material follow-up 都会使旧 build/test/review 证据失效，必须从最终 diff 重新构建和独立复审后再推送。

## 异步弹窗必须先绑定 Promise 结算器，失败结果不得伪装成成功

- DFHIS-31986 的职称选择弹窗先执行 `open()` 并启动职称请求，之后才把外层 Promise 的 `resolve/reject` 写入组件配置；请求极快返回时，组件会在结算器尚未就绪时尝试完成，造成调用链偶发永久 pending。取消、零职称和异常又曾 `resolve({})`，下游将空对象当成成功并继续生成无职称签名。
- 工厂式异步弹窗必须遵循固定生命周期：先创建 Promise 并绑定 `resolve/reject`，再挂载/启动请求；用 one-shot `settled` 门禁统一收口，并在成功、取消、关闭、空列表、字段缺失、请求失败和同步异常的每条出口完成一次且仅一次结算及 DOM 清理。业务失败必须 `reject` 或返回显式失败联合类型，不得用 `{}`、空字符串等成功形态代替。
- 下游在执行写文档、签名、收费或保存等不可逆副作用前，必须校验成功载荷的业务必填字段；开启“必须显示职称”等开关时，空职称应整体中止签名，不能先写姓名/图片再补救。最低专项验证应同时模拟接口极快返回与延迟返回，并覆盖单项、多项、取消、关闭、空列表、字段缺失、请求异常和同步异常，断言 Promise 无永久 pending、只结算一次、loading/按钮恢复、无重复副作用；共享基类还要回归开关关闭路径完全保持旧行为。

## 微前端入口识别与真实控件禁用链

- DFHIS-31831 首轮把医生站来源绑定到可选 URL 参数 `source=zhuyuanysz`，但现场主框架入口没有传该参数，导致默认医生/科室和禁用逻辑全部未触发。跨系统挂载页面不能只凭可选 query 判断来源；应优先使用主框架已下发且经源码证明稳定的应用身份（如 `currentYingYongXx.yingYongId` / 系统应用族），同时保留旧 query 作为兼容兜底。交付前必须覆盖“真实挂载 URL 不带来源参数”和“独立系统入口不误命中”两类回归。
- qiankun 共享 Vue 场景中，全局注册的同名组件可能覆盖页面期望的本地组件。此时外层组件 `$attrs.disabled=true`、模板存在 `:disabled` 或页面呈灰色，都不能证明实际不可修改；必须沿真实组件链检查最终动态组件与原生 input 的 `disabled/readOnly`，并用真实鼠标点击断言值不变、不聚焦、不展开。关键控件若存在同名冲突，应使用唯一局部别名显式注册和引用。
- 权限/限制类前端需求的最低证据应同时包含：来源 computed 命中、提交查询参数固定、真实子组件/DOM 禁用、点击级不可操作，以及一个非目标独立入口仍可编辑的负向回归。静态源码、构建通过或只检查外层 attribute 均不足以放行。前端“不能修改”还需明确不等同于服务端防篡改权限。

## 患者切换、显式查询模式与异步响应所有权

- DFHIS-31967 revision 19 中，首轮只修改了普通日费用清单 `feiYongQd`，用户随后纠正优化版 `feiYongQdOpt` 也属于同一需求。页面名称或菜单文案相近不代表共用实现；改动费用清单、病人查询等存在普通版/优化版/升级版的功能时，实施前必须从菜单配置、内置路由映射和页面目录建立“所有并行入口 → 实际页面组件 → 调用参数”清单，逐个确认同一业务合同是否适用。若多个入口适用，应分别验证默认状态、请求载荷、空结果、患者切换和既有特性，不能用一个页面的 build、截图或 E2E 代替另一个页面。
- DFHIS-31967 revision 20 又暴露了入口上下文的第二层差异：床位牌菜单虽然已经从 `diaoYongCs` 解析 `defaultFeeDeptEnabled=1` 并显式传入上下文，但普通版页面初始化仍优先取 Vuex 全局患者 P，而不是本次床位牌点击患者 Q，造成“上下文患者 Q ≠ 活动患者 P”并隐藏“查询当前科室”。修复这类问题时不能只补 route query；显式菜单/prop 上下文优先于直达 route，当前交互传入患者优先于全局缓存患者，且 `bingRenLb` 嵌入态不得误吃直达路由参数。最低回归必须构造 P≠Q，断言最终活动患者、科室上下文、复选框和请求 patientId 都属于 Q；同时独立覆盖普通版、优化版、直达路由和嵌入菜单，防止一个入口的通过掩盖另一个入口的上下文错配。
- DFHIS-31967 revision 16 把“当前科室 OR / 人工科室 AND”改为显式复选框后，首轮修复只清了复选框标志，遗漏开单/执行科室 K/K，导致新患者仍携带旧患者科室走 AND。查询模式、两个科室值、控件禁用态和请求组合字段必须由同一患者上下文共同初始化/清理；患者不匹配或普通入口重新激活时，要同时恢复历史全部科室和 AND，不能只隐藏复选框。
- 患者页面的异步 conditions/price/list 链必须携带 `patientId + request generation`，在每次响应写状态前、跨 await 后和 data 入口置 loading 前校验；参数与汇总方式应在同一代快照冻结。只在最终列表处判断患者不足以阻止迟到的科室选项、默认 K/K 或金额覆盖新患者，也可能让失效请求把 loading 永久留在 true。
- 外部主患者初始化与页面内关联患者切换是两种入口。`getSelectData(Q, 'all')` 必须先清旧搜索状态并明确优先使用传入的 Q；若先从旧 `searchBar` 读取 P，再 reset，generation guard 虽能拒绝 P 响应，却会连 Q 的整次初始化也丢失。最低回归应包含：P 请求 pending→切 Q→P 迟到不写；旧关联 P→外部主患者 Q→实际请求及写入均为 Q；指定入口→keep-alive 离开→普通入口激活不残留当前科室模式。
- 静态正则或抽象 state 模型可作为快速专项，但不能替代真实页面请求证据。交付前至少抓取勾选时 K/K + OR 标志、取消时保留人工科室且无 OR 标志的实际请求，并对每个被改页面提供 fresh runtime/UI；依赖源 404 等环境限制必须如实记为阻断，除非用户明确接受风险。

## 空数组是权威查询结果，多模式组件必须分离 raw/display 所有权

- DFHIS-31967 revision 18 中，费用明细第一次查询有 44 行，第二次接口返回空数组却仍显示旧表，第三次才清空。根因有两层：展示 computed 用 `tableData.length ? tableData : internalCache`，把合法的 `[]` 误当成“没有新值”；同步调用 `initTableData([])` 时又用 `array.length` 判断是否采用参数，在 Vue2 父 prop 尚未完成本 tick 更新时回退到了上一轮 `allTableData`。
- 查询返回值要按“是否提供”判断，而不是按 truthy 或 `length` 判断。显式数组（包括 `[]`）必须是本次权威快照；只有参数未提供或类型非法时，才允许回退当前 raw。普通模式的展示源应无条件读取父查询 display prop，禁止因空数组回退子组件缓存。最低回归固定为“第一次非空 → 第二次单请求空结果 → 当次表格与合计归零”，并断言无需第三次查询。
- 同一组件同时支持普通查询和费用审核等专用模式时，不要复用一个内部列表同时承担 raw、display 和跨模式兜底。应明确所有权：普通模式 raw/display 由父组件持有；审核模式用独立 `auditRaw/auditDisplay`。筛选始终从对应 raw 重算到对应 display，普通父响应不得覆盖审核数据，审核筛选不得借道修改普通父 prop。测试必须补“审核非空 → 状态筛选为子集/空 → 切回全部恢复原始集”，并确认表格、合计和操作选择统一消费同一 display。

## 字典扩展属性位串与消费方长度假设

- `gy_jibing.jibingkzsx`、`gy_shousuxm` 等扩展属性是**定长位串**，每一位的语义由字典类别维护（如疾病 `daimalb=10211`、手术项目 `daimalb=10212`，daimaid 即位次）。
- 通过 SQL 新增位次（如第 6 位"中医日间"）后，必须检查消费该位串的前端组件/后端代码是否有**写死的长度假设**。DFHIS-31833 中共享组件 `KuoZhanCheck`（df-web-zhushujugl）位串模板写死 5 位 `'00000'`，导致第 6 位在页面上无法勾选（第三次重打开）。
- 交付此类数据变更时，自测标准不是"数据落库成功"，而是"新位次在页面上真的能勾选、保存、回显"。

## 配置化导出的字段顺序

- 配置表或视图定义的字段顺序是导出合同的一部分，不能把 `JdbcTemplate.queryForList` 返回的 Map 顺序当成业务顺序。DFHIS-31955 首轮修改虽然补齐了 HQMS 医嘱导出字段，但没有按配置列显式重建结果，导致导出顺序偏离视图/配置顺序。
- DFHIS-32015 经二次用户纠正后明确：配置存在和配置缺失不能各写一套字段解析逻辑。`columns` 非空时它只负责形成 SQL 投影，null/空串/空白时投影为 `*`；两种情况都必须走同一条 `ResultSetMetaData` 路径，按 `1..columnCount` 用 `getColumnLabel(index)` 和 `getObject(index)` 写入 `LinkedHashMap`。禁止在 Java 中 `split(columns)` 后按名称取值或自行 upper/lower，禁止 `V_Hqms_YiZhu`/`BeanPropertyRowMapper`、固定字段清单或 `queryForList` 约束返回；否则配置别名、混合大小写标签、表达式和视图未来新增字段仍会被代码写死。
- 修复同类方法时要先检查 Git 历史和当前调用链：方法可能已从病案号查询改名或收紧为住院流水查询。列序修复不得顺手回退 `jzlsh`、院区或权限过滤；只修改目标导出类型，避免影响其他按钮。
- 交付前至少验证三层顺序一致：数据库视图物理列顺序、配置投影顺序、实际导出字段顺序，并同时覆盖动态新增字段、配置别名、混合大小写标签以及 `columns` 非空、null、空串和纯空白。测试不得把需求附件的固定 73 列抄成实现合同；要使用实体类中不存在的任意未来字段，并让按字段名读取直接失败，才能证明实现真正只依赖结果集元数据。单看 SQL 文本、代码 diff 或 JSON 内容齐全不能证明顺序正确，发布后仍须核验实际导出文件。

## 数字控件事件时序与多行业务状态

- DFHIS-31915 在纯函数测试、生产构建和单序列号截图都通过后仍再次打开：真实 `df-input-number` 的原生 `keydown` 可早于 `v-model` 同步，因此键盘输入 5 后 Enter 仍可能读到旧值 1；成功分支又无条件清空当前批次，导致数量回 1 并禁用。
- 错误做法是把数量合并 helper 的正确性、源码字符串断言或单行业务截图当成控件交互证据。这些证据不能证明键盘/`change` 事件顺序、`disabled` 状态、焦点和 DataGrid 真实勾选已收敛。
- 修改数字控件驱动的多行选择、批量录入或数量调整流程时，交付前必须在真实宿主中挂载真实控件和表格，使用至少 6 条实际可用行执行事件级 E2E。至少断言：Enter 5 后显示 N=5、选中 5、未禁用、焦点在数量框；同批 5→3→6 每次数量与勾选数一致；重新扫码、删除、生成或返回等边界按合同清理状态；目标 Promise/控件运行时错误为 0。
- 若真实多行数据受科室对照、租户或权限配置阻断，可以在浏览器已挂载组件内使用不落库的最小运行时测试夹具验证前端事件时序，但必须记录夹具内容和限制，且不得把该证据表述为正式科室对照下的联合发布验收。

## 连续扫码的焦点、选区与证据边界

- DFHIS-31915 第 4 轮重打开说明：只断言“焦点回到某输入框”仍不足以支持扫码枪连续录入。若旧值未保留或未全文选中，下一次扫码会追加文本，操作员仍需手工清空；验收必须同时断言输入值、`activeElement`、`selectionStart` 和 `selectionEnd`。
- 数字控件的 Enter 与 `change`/步进器可能具有不同产品语义，不能共用一个无来源标识的成功收尾。正确做法是显式分流：键盘 Enter 可应用后回扫码框并全选旧 UDI，步进器或滚轮 change 可应用后留在数量框并全选数量；同时保留当前批次，直到新扫码、删除、确认或关闭才清理。
- 评论文字、原型图和上一轮用户选择发生冲突时，必须把冲突写进 Requirement Contract 并取得新决策；精确文案必须以原始附件目检为准，不能依赖 reviewer 的转述。DFHIS-31915 曾因评审者误读图二中的“多个序列号”为“多个可用序列号”产生伪阻断，复评必须回到原图逐字核对。
- 浏览器 `insertText`、直接调用组件 Enter 方法等夹具可以证明已挂载组件的焦点/选区和覆盖逻辑，但不能称为物理扫码枪证据；交付结论要明确其只放行前端代码，正式科室配置、真实扫码枪和共享入口仍属于联合发布验收。

## 异步字典与表格内部列快照

- DFHIS-31797 首轮代码已成功请求 `daimalb=10435`，组件状态中也有五项，但页面仍固定显示三项。根因是实际渲染组件 `DfXTable` 在 `columnStrict=true` 时于创建阶段把源 `columns` 深拷贝到内部 `renderColumns`，且不监听后续源列变化；只原地修改 `columns[].form.dicData` 不会刷新真实控件。
- 排查动态列或异步字典问题时，必须先确认页面实际使用的表格封装及其列生命周期，不能把另一个底层表格的 watcher 机制套用过来。修复应更新源列，并通过该组件公开 API 重建内部列；本案例是在 `$nextTick` 调用 `ref.updateColumns()`。不要把这一做法泛化到所有表格组件。
- API 200、组件字典数组正确、源 `columns` 引用变化或纯函数测试都不足以证明修复完成。最低证据应同时断言目标列重建方法被调用，并在真实宿主中展开实际下拉检查选项；若正式业务列表为空，可在已挂载真实组件内使用不落库最小行夹具，但必须明确它只证明前端取数与渲染，不等同正式患者保存、共享入口或生产数据发布验收。

## 护理事件唯一标志、自动导入策略与死亡路径分层

- DFHIS-29664 第一轮独立评审发现：`GY_HuLiDjXm.weiYiBz`（事件是否唯一）与 `shiJianZdDrBz`（不自动导入 / 作废后再次导入 / 只导入一次）是两个独立业务维度。错误实现为了支持召回后二次出院，把自动导入值 1、2 合并为只查询未作废记录，破坏了值 2“包含作废、只导入一次”的原职责。
- 修改体温单自动事件时必须分两层判断：先按 `shiJianZdDrBz` 决定是否自动导入以及历史查询是否包含作废，再按 `weiYiBz + 未作废` 判断唯一结束事件是否阻断。禁止用自动导入标志代替唯一标志，也禁止为了放开非唯一事件而抹平值 1/2 的作废语义。
- 同一次业务事件的幂等键应优先使用稳定业务事实，如“病人住院 ID + 事件类型 + 预出院/测量时间”。时间变化可代表召回后的新一次出院；相同时间的重复页面调用不得重复新增。若实现是“查询后判断再插入”且没有数据库唯一约束或锁，只能声明顺序调用幂等，不能宣称并发强幂等。
- 需求若限定“出院事件自动生成时候”增加门禁，门禁只能包住普通出院路径。DFHIS-29664 初稿把整个出院/死亡共用方法包在唯一结束事件门禁下，导致已有唯一事件时死亡路径也可能被跳过。交付前必须单独回归：普通出院被正确阻断、死亡仍作废旧出院并生成死亡、婴儿/转科等排除场景保持原行为。
- 最低自动化证据应覆盖：参数 0 固定结束事件、参数 1 配置结束事件、唯一/非唯一、作废/未作废、自动导入值 0/1/2、同时间重复、时间变化、死亡不受出院门禁影响，以及对应 repository 查询选择。仅测试纯 helper 不足以证明调用链未接错；至少增加仓储交互测试，条件允许时再补真实数据库集成验证。

## 事务 outbox、乱序远调与补偿可达性

- DFHIS-31945 的病案接收需在本地提交后回写住院状态。初稿只在 `afterCommit` 回调里创建补偿记录，存在“本地已提交、进程在补偿行落库前退出”的丢事件窗口。正确做法是把 PENDING outbox 写入当前业务事务，业务回滚时同退、提交时已持久化；`afterCommit` 只负责首次消费，定时任务负责恢复未消费事件。
- 同一业务键可能连续产生不同目标状态，不能只在远调前查一次“是否为最新”。旧请求可能已在途，新请求先完成，旧请求最后成功或因超时抛异常但远端其实已生效，都会把远端状态回退。每条事件应携带单调版本；成功和异常路径都必须在远调返回后再次检查版本，过期事件标记 OBSOLETE，并立即重放当前最高版本，确保最终收敛。若远端支持版本/CAS，应优先在远端原子拒绝旧版本；否则至少提供同业务键串行化或上述二次检查重放。
- 补偿任务分页必须先在数据库筛选“可重试状态 + 已到期时间”，再排序并 limit。先取最老 100 条、再在内存过滤未到期记录，会让持续失败或长退避的老事件长期占满窗口，使后续已到期事件饥饿。
- 多种远端调用语义（如普通状态更新与“仅已归档时更新”）必须作为 outbox 字段持久化，首次消费和重试使用同一分支，禁止失败后降级成另一接口。最低验证应覆盖：主事务回滚、提交后进程退出、远端超时但实际生效、旧/新事件乱序、成功与异常后二次淘汰、双实例重复消费、Top-N 到期查询，以及最终远端状态收敛；构建通过或日志记录不能替代这些测试。

## 第三方（互联网医院）回写入口在 mic-sapi，不是业务模块各自新增 Controller

- DFHIS-31879 V1 在 `df-mic-jj-zhuyuan`、`df-mic-lc-zhuyuan` 各自新增回写 Controller（`BingAnSyController.saveZhenDuanZlHuiXie`、`BingRenYzController.saveYiZhuHuiXie`）并已编译合并到 RC，需求变动后才通过云效评论确认：第三方/互联网医院回写 HIS 走统一对外层 **`mic-sapi`（仓库 `df-sapi`，包 `com.df.cbhis.mic.sapi`）**，不是各业务模块自己的 Controller。结果 V1 三个住院端点全部作废、需 revert RC。
- 第三方回写真实入口：`mic-sapi/BingRenXxController#shengChengMenZhenBl`(生成门诊病历,`DTO_KaiDanBlXx`) / `shengChengTiZhengXx`(体征,`DTO_ZJ_JiuZhenTzXx`) / `shengChengZhenDuanXx`(诊断,`List<DTO_ZJ_ZhenDuan>`)，调用链 `mic-sapi → menZhenBingLiApi`(`df-his-api/mic-lc-menzhenjz-api`)`→ df-mic-lc-menzhen`，是**门诊**回写；`mic-sapi` 还提供 `MessageController#sendMessage`(`POST /message/sendMessage`,`Dto_Message`)，是三方会写后向医生站推送消息的能力来源。
- 正确做法：评审/实现"第三方/外部系统回写 HIS"类需求时，先 grep `shengCheng*`、`mic.sapi`、`df-sapi`、互联网医院对外接口文档 定位真实对外入口，确认第三方实际调用哪个 Controller 及其下沉调用链，再决定改动落点；不要假设需求里提到的业务实体表（如住院诊断/处方）对应的业务模块 Controller 就是第三方入口。新增回写能力优先挂在 mic-sapi 现有 `shengCheng*`/对外 Controller 或其下沉 API，而不是在 jj-/lc-/mic- 业务仓库里另起端点。
- 注意 `df-sapi` 仓库自带 `mic-sapi-api`（项目内 *-api 模块，属废弃 API）；mic-sapi 的 `shengCheng*` 是 HTTP Controller（非 df-his-api Feign），改它本身不触碰 df-his-api 红线，但若要新增对外 DTO/Req 契约，仍须评估是否应走 `df-his-api` 而非项目内 `mic-sapi-api`。
- df-his-api 发布是真实 CI 硬阻断：`df-his-api` 在 `192.168.1.150:8081` 与 `192.168.1.56:8080` 两套 Jenkins 均**无 job**（catalog 无映射 + Jenkins API 查无），`his-workflow-harness` 的 `company-environments.json` 也无其条目。因此任何需要 df-his-api 发新 jar 才能编译的改动（如新增 Feign 契约 `BingAnSyApi.saveZhenDuanZlHuiXie`），下游（mic-sapi 等）在管理员补 job / 手动发布前**无法 CI 编译**。规划 df-his-api 契约变更时，必须把"jar 无法经 CI 发布"列为阻断并标明需管理员介入，不要假设能像普通服务那样触发 Jenkins 编译。

## 三方会写后前端刷新：方案先决策再实现，优先消息推送而非轮询

- DFHIS-31879 V1 把"门诊三方会写后自动刷新"实现为前端 `setInterval` 30s 轮询（`df-web-menzhenysz` `menZhenBl/index.vue`），需求变动被产品明确否决，改为：第三方回写接口调用后由后端发消息，医生站前端收到消息后**主动刷新**，参数【门诊病历_三方会写后自动刷新】改为控制"是否发消息"而非轮询开关。V1 评审其实已确认 `df-web-menzhenysz` 前端**无 WebSocket/SockJS/EventSource 基础设施**，却仍选了轮询。
- 错误做法是在产品/架构未拍板刷新方案前就实现并 push 代码。涉及"刷新/实时性/三方会写感知"的需求，必须在 Requirement Contract 里作为阻断项先决策（前端轮询 vs 后端消息推送 vs 长连接），方案与默认值、参数语义、失败兜底一起拍板后再写代码；类似地，"第三方实际调用哪个接口"也属实现前必须用代码证据确认的阻断项，确认前不要 push 业务端点。
- 正确方向：消息推送优先复用现有通道——`mic-sapi MessageController.sendMessage` + HIS 现有消息/事件通道 + 前端订阅，避免新建 WebSocket（前端无 WS 基础设施，新建鉴权/重连成本高）。前端确无长连接时，"轻轮询消息中心、收到再刷"可作折中，但不得退回"直接轮询刷数据"。
- V2 已验证落地路径（DFHIS-31879 门诊消息闭环，已 push + `yarn build` 通过）：后端 `mic-sapi` 的 `shengChengMenZhenBl/TiZhengXx/ZhenDuanXx`（`BingRenXxController`，落库后按参数判断）构造 `Dto_Message` 强制 `xiaoXiFlId=DISANFANGXX` 调 `messageServiceApi.sendMessage`，由 df-message-service 按 `jiuZhenId` 投递接诊医生；前端**无需新建 WebSocket**——`df-web-main` 门户已有 WS，`df-web-menzhenysz` `App.vue#handlerDoctorStation`（约 :273）已订阅 `globalEvent` 并按 `xiaoXiFlId` 分发（原有 '3'/'5'），新增 `'99'` 分支经 `$bus` 触发 `menZhenBl` 子区域静默刷新即可（先例：药房开放时间 `SOCKET_BUSINESS_EVENT`）。即"复用现有通道"在本仓已被证实可行，下次同类需求直接按此链路实现，先别假设前端无长连接。
