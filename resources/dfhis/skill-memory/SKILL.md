# Skill Memory — 经验教训自动沉淀机制

把任务中产生的经验教训固化到正确的技能包，而不是散落在聊天记录里。本机制**默认自动执行**，不依赖用户显式指令。

## 自动判断规则（任务收尾时静默执行）

每次需求交付、修复验证通过、或阶段性任务收尾时，自动回顾本次会话，逐项判断：

1. **返工信号**：需求被重打开、测试打回、同一问题修了两轮以上 → 必沉淀（根因 + 错误做法 + 正确做法）。
2. **纠正信号**：用户纠正了 agent 的做法、口径或假设 → 必沉淀。
3. **新知信号**：发现了文档和代码里没写、但下次还会用到的可复用事实——业务口径、表结构、字典位串、环境细节、排障路径、工具链坑 → 沉淀。
4. **过滤**：一次性、不可复用的信息（临时状态、特定某次的数据、个人偏好）→ 不沉淀，不提及。

任一信号命中 → 立即按下面流程沉淀，**不询问用户、不等待指令**；在交付汇报末尾用一行说明去向（写进哪个技能、新建还是更新）。全部未命中则什么也不做，也不在汇报中提及本机制。

用户显式要求（"记住""吸取教训""以后别忘了""沉淀成技能"）时，无论信号强弱都执行。

## 执行流程

### 1. 梳理现有技能

先列出当前全部可用技能并读 description，判断经验归属，不凭记忆新建重复技能。

### 2. 分类路由（决策表）

| 经验类型 | 去向 | 现有技能 |
|---|---|---|
| 云效归档/评论/字段回写/交付流程 | 更新现有流程技能 | `yunxiao-requirement-archiver`、`yunxiao-contacts` |
| HIS/DFHIS 业务口径（表结构、字典位串、诊断类别、医保、规则引擎、参数） | 匹配到现有业务技能则更新；无匹配且可复用则**新建独立 `dfhis-*` 技能** | `dfhis-reopen-lessons`、`dfhis-yibao-dmdz`、`dfhis-company-environment` |
| 构建/验证/发布/合并流程 | 更新现有流程技能 | `his-workflow-harness`、`his-release-merge` |
| 通用需求交付方法论 | 更新现有技能 | `requirement-delivery-flow` |
| UI 规范 | 更新现有技能 | `ui-spec-review` |
| YGT/医共体 | 更新现有技能 | `ygt` |
| 跨多个技能的通用教训（如重打开自查） | **新建独立技能**，其他技能只放一行指针 | 先例：`dfhis-reopen-lessons` |
| 一次性、不可复用的信息 | 不沉淀 | — |

路由原则：

- **通用流程归通用流程技能**：云效流程只写进 `yunxiao-requirement-archiver`，不掺业务内容。
- **HIS 业务归独立业务技能**：业务口径教训优先新建独立 `dfhis-*` 技能，不塞进流程技能或环境资料文件。
- **同类流程合并**：与现有技能主题相同的，更新现有技能，不新建。
- **跨领域才新建通用技能**：任何单一技能都装不下的，新建独立技能并互相放指针。

### 3. 写入规则

- **单一来源**：一条经验只写在一个技能里，其他技能用一行指针引用，禁止复制内容重复维护。
- **带事故证据**：每条经验写明真实来源（需求号、根因、错误做法、正确做法），不写空泛口号。
- **可操作**：写成"交付前/操作时要做什么"的检查项或规则，不是感想。
- **frontmatter 完整**：新技能必须有 name 和带触发关键词的 description，保证能被检索触发。
- **交叉引用**：新技能列出关联技能；被引用的技能在合适位置加一行指针。

### 4. 校验与汇报

- 检查新/改技能的 description 触发词能覆盖今后的自然表述（如"重打开""吸取教训"）。
- 确认无内容重复：同一教训在全部技能中只出现一份正文。
- 用一行汇报：经验分到哪类、写进哪个技能、新建还是更新、指针加在哪。

## 团队共享

本技能随 Orca 的 DFHIS workflow pack 分发给全队。成员各自沉淀的本地技能会由 Orca 定时上传到团队服务端（技能贡献 → 每日 LLM 整理进技能池 → 收录进官方技能包）；高价值经验可在服务端"技能包贡献管理"页右键"放入技能池"加速共享。沉淀为团队共识、需要长期随包分发的技能，应像本技能一样合入 Orca 仓库的 `resources/dfhis/`。
