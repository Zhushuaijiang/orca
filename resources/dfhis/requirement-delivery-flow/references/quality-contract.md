# 从需求到开发测试的质量契约

适用：复杂、多入口、跨服务或重打开的需求。小型低风险变更按影响缩减；不按文档数量判断质量。

## 编排分工与顺序

| 阶段          | 主责技能                                 | 必须交给下一阶段的结果                                      |
| ------------- | ---------------------------------------- | ----------------------------------------------------------- |
| 归档/版本事实 | yunxiao-requirement-archiver             | 原文、评论/附件、当前状态、指定分支和仓库 SHA；旧记录标日期 |
| 需求决策      | requirement-contract-gate                | 当前有效规则、来源、真正未决事项；已确认决策不重复询问      |
| 拆解/协调     | requirement-delivery-flow                | 按用户操作与状态转换拆分的验收点，以及跨层影响和集成顺序    |
| 实现          | 适用领域技能                             | 每个验收点的实现位置、调用方、兼容及恢复路径                |
| 自测/构建     | his-workflow-harness + 对应测试技能      | 实际执行命令、结果、范围、最终版本；编译不充当单测          |
| 页面/业务验证 | dfhis-ui-test-delivery + dfhis-e2e-reuse | 正常入口到实际业务结果；UI 扫描另由 ui-spec-review 负责     |
| 合并          | his-release-merge                        | 目标分支最终语义、依赖版本、冲突处理及受影响的重验结果      |
| 提测          | yunxiao-requirement-archiver             | 验收点与测试反馈闭环、版本/环境和可复现步骤；执行回写后读回 |
| 经验维护      | skill-memory                             | 已核实的可复用教训落一个正本，其他入口只引用                |

这些是职责划分，不要求每次加载所有技能。通用协调技能不重写领域规则、测试运行器或云效回写规则。

## 先写验收映射，再分文件任务

对每条有业务影响的规则记录：`验收点 ID → 原文/评论/有效决策 → 前置与入口 → 动作 → 可观察结果 → 实现/消费端 → 用例 ID → 执行证据`。测试反馈单列 ID，不能用一个笼统“回归通过”覆盖多个不同症状。预期来自业务规则，不从新实现反推。

拆解以一个可验收的操作或状态转换为单位；仓库/文件是实现映射，不是验收单位。跨服务任务明确请求字段、返回/异常、唯一键、数量/金额口径、写入事务与后续消费者。只有任务都完成但没有集成验证时，仍不能转开发测试。

1:N、计费、库存、权限或状态机改变时，按实际风险选用：多条同时操作、部分成功、撤销/退回、重复提交、重试、并发、旧数据、跨入口。数量/金额须对账明细与汇总，失败要检查不应发生的持久化副作用。不可把这些统一降为低优先级边界项。

## 三个可检查的交接条件

1. **可开发**：关键业务歧义已有有效决策，验收点与影响面明确。无须把常规实现选择升级为用户确认；未决事项只阻塞依赖它的工作。
2. **可提测**：最终版本的适用测试/构建通过，主流程与原始反馈在代表性环境实际验证；真实数据结果、受影响入口及必要恢复路径一致。未执行、空数据、只出现按钮、模拟成功不等于通过。生产验收可以后续进行，开发自测不能留给测试人员代做。
3. **可合并/发布**：按用户授权范围执行；核对目标分支最终行为与运行包。冲突、回滚、依赖变化使受影响证据失效，重新验证这些范围；无关证据不必机械全跑。

命令 `exit 0` 只说明该命令成功。未知命令标 `command`，构建标 `build`，测试标 `passing_test`，截图标 `screenshot`；还须读测试数量/跳过项与业务断言，零用例不构成测试通过。技能自测通过只证明工具回归，不证明业务需求通过。

HIS 重打开需求的更细证据规则和可执行提测检查复用 [reopen-audit.md](../../dfhis-reopen-lessons/docs/reopen-audit.md)，不另建竞争门禁。校验器只能检查声明一致性，不能替代证据核验或授权。

## 单一来源与范围

用户只要求排查/审查时，产出分析和证据；不自动修业务代码、转状态、发消息或部署。已有有效授权持续生效，不重复索取。缺少归档中的确认记录不等于从未确认，先查会话/会议结论。

同名技能发现多个目录时，核对当前宿主的入口和正文来源。维护一份正文，其他入口明确转向正本并从正本执行脚本；不复制旧脚本执行，不把本地更新称为团队包已更新。发布团队包前需要单独做打包路径与目标环境验证。
