# HIS 提示词蓝图

## 分层组合

HIS 提示词应由以下层次组合，避免把所有内容塞进一个长期 system prompt：

1. 稳定核心：角色范围、证据等级、授权边界、失败语义、安全规则。
2. 环境适配：当前机器实际存在的仓库、知识库、工具和输出位置；启动时发现或由 `AGENTS.md` 注入。
3. 领域规则：门诊、住院、医保、药房药库、病历、报表等专项技能，仅在命中时加载。
4. 当前任务：用户目标、输入、验收标准和明确授权。云效需求与缺陷的阶段与六维对照以 [requirement-six-view-prompt.md](requirement-six-view-prompt.md) 为准。
5. 运行证据：本次读取的代码、Schema、SQL、配置、工作项和测试输出，不写回稳定提示词。
6. 长期记忆：只保存稳定、声明式偏好与环境事实；不保存密钥、患者数据、任务进度、临时错误或很快失效的状态。

这能降低上下文成本，也避免动态数据、秘密和过期路径污染所有会话。

## 推荐骨架

按任务规模裁剪，不要求每个标题都出现：

```text
角色与目标
- 服务对象、业务范围、预期结果

权限与边界
- 默认只读还是允许实施
- 哪些动作必须获得额外授权

意图路由
- 普通咨询 / Schema-SQL / 业务流程 / 代码链路 / 云效需求 / 实施改造 / 运维
- 每类任务命中的领域技能和权威证据源

证据契约
- 已证实、推断、未验证的定义
- 标识符与关联关系的最低验证要求
- 来源冲突时的优先级

工具与上下文预算
- 只加载最小必要技能
- 并行获取独立证据
- 搜索结果过多时如何收窄

失败处理
- 超时、限流、权限、格式异常、证据缺失
- 部分完成时必须保留哪些已验证结果

交付契约
- 结论优先
- 证据、边界、下一步
- 代码修改后的产物与验证

安全与自检
- 秘密、患者数据、外部写操作
- 假成功、内部过程话术、悬空引用
```

## 设计判断

- 把“所有部分相关技能都必须加载”改为精确路由，否则会与“少上下文、强证据”冲突。
- 把工具名和绝对路径放在环境适配层。只有当前环境确认可用时，才要求“先用某工具”。
- 把输出格式写成任务合同，不写成固定长模板。简单问题可以一句话；复杂问题才需要证据表或入口矩阵。
- 把“必须修改”“必须发布”等动作与用户授权分开。提示词不能自行扩大权限。
- 把错误恢复写成可观察状态：成功、部分完成、失败/阻断。不得让错误字符串落入成功答案。
- 重要规则说明验证条件与原因，避免大量无上下文的“铁律”互相冲突。

## 安全门禁

提示词和记忆中禁止出现真实的：

- API key、访问令牌、密码、Cookie、私钥、带口令连接串
- 患者姓名、证件号、卡号、住院号、病历正文等非任务必要数据
- 可直接操作生产环境的未脱敏凭据

使用 `${SECRET_FROM_ENV}`、`<redacted>` 或秘密管理器位置表达依赖。若旧提示词已含真实秘密，先移除并按组织流程轮换；不要在评审报告中复述原值。

## 冲突审查

发布提示词前检查这些常见矛盾：

- “最小必要上下文”与“部分相关也全部加载”同时存在
- “默认只分析”与“持续做到完成”没有区分授权范围
- “必须用固定工具”但该工具并非所有环境可用
- “固定分支/worktree 规则”覆盖了仓库自己的发布技能
- “简洁回答”与强制长篇固定章节同时存在
- “不泄露秘密”但提示词或记忆已经直接注入秘密
