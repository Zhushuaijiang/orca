# HIS 任务交付合同

## 普通解释与配置咨询

优先给直接答案。只有事实依赖当前系统实现时才查证；不要为简单问候、术语解释或连通性测试加载重型技能。若配置因医院、版本或院区而异，明确本地差异和核验入口。

## Schema、表关联与 SQL/报表

1. 从当前环境声明的权威 Schema 和已有报表/SQL 取证。Grok 会话查表/字段/标准卡/报表走技能 `his-mcp-knowledge`，不要 clone `df-knowledge`。
2. SQL 中每张表、每个字段都要验证存在；连接键还要验证两端字段和关联依据。
3. 主键、唯一键、代码/SQL 明确使用的关联可列为已证实；只靠名称相似的放在推断，不得写入生产 SQL。
4. 字典值、退费冲销、院区、租户、时间和金额口径若无法从静态 Schema 得到，提供探查 SQL 或要求实库证据。
5. 交付可执行 SQL 时给参数、数据库方言、口径、已验证对象和只读/写入风险。数据修复 SQL 默认不直接执行。

本地已建立“报表即 SQL”的约定时直接交付 SQL；否则先根据上下文判断用户要查询语句、报表文件还是口径说明。

## 业务流程与故障排查

用最短证据链回答这些问题：谁在什么入口操作、经过什么状态、调用什么服务、读写哪些数据、受什么参数/权限影响、失败后如何恢复。

排障优先输出：

- 最可能根因与判断依据
- 从上游到下游的检查顺序
- 每一步的可观察信号或只读 SQL
- 正常业务恢复入口优先于直接改库
- 未验证的版本差异、配置差异和数据风险

## 代码调用链与数据落库

先确认用户问的是调用关系、业务含义还是实际落库。完整链路通常包括：

`页面/任务/消息 → API/Controller → Application/Service → Repository/SQL → 表/字段`

引用文件与符号时给当前真实路径和行号或稳定符号名。表字段要再与 Schema 交叉验证。调用图、代码搜索和旧知识图谱只能证明各自覆盖的层级；证据不足时不要声称“全链路已确认”。

## 云效需求与影响范围

读取标题、正文、验收标准、评论、关联项、附件和图片。HTTP 200 的登录页或无权限页仍是读取失败。把结果拆成：

- 明确要求
- 隐含影响与入口矩阵
- 当前代码证据
- 待澄清或阻断
- 最小改动与验证范围

“给 X 也加上 Y、与 Z 一样”或跨模块同步类需求需要枚举业务对象、角色、入口、仓库、页面、接口、状态和输出物，不能只命中第一个文件就收口。需求与缺陷共用六维对照；阶段、证据方法和裁剪规则以 [requirement-six-view-prompt.md](requirement-six-view-prompt.md) 为准。

## 实施与代码修改

只有用户明确要求改动时实施。开始前读取目标仓库的 `AGENTS.md` 与发布/单测/前端交互等专项技能；分支、worktree、提交和发布规则以目标仓库约定为准。

完成标准包括真实产物与适度验证：变更文件、关键 diff、构建/测试/静态检查或可观察运行结果、未覆盖风险。未经授权不发布、不回写外部工作项、不执行生产数据修复。

## 输出模板

简单问题可以只有：结论 + 一个关键依据。

普通分析建议包含：

```text
结论
最相关证据
边界/未验证项
下一步
```

复杂分析建议包含：

```text
结果摘要
证据链或入口矩阵
业务/技术分析
风险与未验证项
建议动作和验收办法
```

模板为信息合同，不要求机械输出标题。用户要求简洁时合并章节；用户要求代码原文时只引用理解问题所需的片段。

## 失败与部分完成

- 超时：保留已取得证据，指出尚未证明的判断；收窄问题或分段重试。
- 429/配额：标记失败，说明恢复时间或替代模型/路径；不能把错误文本当业务答案。
- 权限或登录页：说明实际返回和缺失材料，不按标题推断。
- 工具结果过大：先搜索符号和候选，再读取局部；不把整库输出塞进上下文。
- 引用丢失：重写为自包含答案，不说“见上面”或“用前面的 SQL”。
